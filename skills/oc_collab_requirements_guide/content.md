# OC-Collab 需求编写指南

## 快速开始

### 创建新需求文档

```bash
# 1. 先做需求分析
#    分析所有历史文档，识别可用Skill解决的问题
#    分析结果输出到 ANALYSIS_vX.X.X_Requirements_Analysis.md

# 2. 复制模板
cp docs/01-requirements/TEMPLATE_requirements.md docs/01-requirements/requirements_vX.X.X_DRAFT.md

# 3. 编辑文档
#    - 填写所有必须字段
#    - 明确验收标准
#    - 预估工时

# 4. 状态流转
#    DRAFT → READY (产品完成) → APPROVED (开发确认)
```

## 需求分析环节 ⭐

**创建需求文档前，必须先做需求分析**

**核心原则**：所有进入需求文档的功能，**必须经过需求分析**。

```
需求来源
    │
    ├── Proposal ──→ 需求分析 ──┐
    │                          │
    ├── Memo ───────→ 需求分析 ──┼──→ 分类决策
    │                          │
    ├── Bug Report ──→ 需求分析 ──┤
    │                          │
    └── 其他 ────────→ 需求分析 ──┘
                              │
                    ┌─────────┴─────────┐
                    │                   │
               ┌────▼────┐         ┌────▼────┐
               │ 用Skill │         │ 需开发  │
               └─────────┘         └────┬────┘
                                         │
                                   创建需求文档 ✅
                                   (需要评审)
```

**关键规则**：
| 规则 | 说明 |
|------|------|
| 需求必须来源 | 需求文档中的需求必须来自需求分析 |
| 禁止直接添加 | 不能跳过需求分析直接创建需求文档 |
| 入口唯一 | 需求分析是进入需求文档的唯一入口 |

### 为什么要做需求分析？

| 原因 | 说明 |
|------|------|
| 避免重复造轮子 | 先查历史，避免重复实现已有功能 |
| 识别Skill机会 | 80%流程问题可用Skill低成本解决 |
| 明确开发范围 | 区分必须代码实现 vs 可用Skill替代 |
| 吸取历史教训 | 分析Bug、Memo避免重复踩坑 |

### 核心概念澄清

| 概念 | 说明 | 是否需要评审 |
|------|------|--------------|
| **Proposal** | 解决方案建议 | ❌ 不需要 |
| **Skill** | 流程规范指南 | ❌ 不需要 |
| **需求文档** | 正式纳入版本的功能定义 | ✅ 需要评审 |
| **PARKED** | 推迟的功能 | ❌ 不需要 |

### 需求分析步骤

```bash
# 步骤1: 收集相关文档
ls docs/01-requirements/PROPOSAL*.md   # 提案
ls docs/00-memos/MEMO*.md               # 备忘录
ls docs/00-memos/BUG*.md                # Bug报告
ls skills/*.md                          # 现有Skill

# 步骤2: 分析每个问题/需求
#    - 问题来源？根本原因？
#    - 可否用Skill解决？
#    - 是否必须CLI实现？

# 步骤3: 分类决策
#    ┌─────────────────────────────────────────┐
#    │ 决策类型       │ 下一步                │ 是否评审 │
#    ├─────────────────────────────────────────┤
#    │ ✅ 用Skill   │ 编写/更新Skill文档     │  不需要  │
#    │ 💻 需开发   │ 创建需求文档          │  需要    │
#    │ ⏸️ 推迟    │ 放入PARKED            │  不需要  │
#    │ ❌ 放弃    │ 关闭Proposal          │  不需要  │
#    └─────────────────────────────────────────┘

# 步骤4: 输出分析报告
docs/01-requirements/ANALYSIS_vX.X.X_Requirements_Analysis.md
```

### 需求分析报告模板

```markdown
# vX.X.X 需求分析报告

## 一、分析方法论

### 1.1 分析范围
本报告基于对以下文档的分析：
- Proposal（提案）：X个
- Memo（备忘录）：X个
- Bug Report（Bug报告）：X个
- Skill（技能指南）：X个

### 1.2 分析框架

| 维度 | 说明 |
|------|------|
| 问题来源 | 从哪个文档发现问题 |
| 根本原因 | 深层问题分析 |
| 解决方案 | Skill / 需开发 |
| 优先级 | P0 / P1 / P2 |
| 决策 | 用Skill / 需开发 / 推迟 / 放弃 |

## 二、问题与需求清单

| 编号 | 问题/需求 | 来源 | 决策 | 下一步 |
|------|-----------|------|------|--------|
| Q-001 | xxx | PROPOSAL_xxx | 用Skill | 更新/创建Skill |
| Q-002 | xxx | MEMO_xxx | 需开发 | 创建需求文档 |
| Q-003 | xxx | BUG_xxx | 推迟 | 放入PARKED |

## 三、解决方案分类

### 3.1 用Skill实现（无需代码开发，不需要评审）
| 编号 | 功能 | 现有Skill | 操作 |
|------|------|----------|------|
| S-001 | xxx | oc_collab_xxx_guide | 更新/创建Skill |

### 3.2 需开发（需要代码实现，需要创建需求文档并评审）
| 编号 | 功能 | 工时 | 优先级 |
|------|------|------|--------|
| C-001 | xxx | Xh | P0 |

### 3.3 推迟（不需要评审）
| 编号 | 功能 | 原因 |
|------|------|------|
| D-001 | xxx | 优先级低 |

## 四、vX.X.X 范围定义

### 版本目标
...

### 功能清单
...

## 五、决策依据
...
```

### 关键澄清

| 文档类型 | 是否需要评审 | 依据 |
|----------|--------------|------|
| Proposal | ❌ 不需要 | 解决方案建议 |
| Skill | ❌ 不需要 | 流程规范 |
| 需求文档 | ✅ 需要 | 正式功能定义 |
| Memo | ❌ 不需要 | 经验总结 |
| Bug Report | ❌ 不需要 | 问题报告 |

### 决策后的下一步

| 决策 | 下一步行动 | 是否需要创建需求文档 |
|------|-----------|-------------------|
| 用Skill | 编写/更新Skill文档 | ❌ 不需要 |
| 需开发 | 创建需求文档 | ✅ 需要 |
| 推迟 | 放入PARKED_vX.X.X.md | ❌ 不需要 |
| 放弃 | 关闭Proposal | ❌ 不需要 |
```

### 历史文档分析清单

| 文档类型 | 检查重点 |
|----------|----------|
| **Proposal** | 功能需求、解决方案、工时预估 |
| **Memo** | 根本问题分析、教训总结 |
| **Bug Report** | 已发现问题、系统缺陷 |
| **Skill** | 现有流程规范、已覆盖场景 |
| **Meeting Notes** | 协作流程、决策记录 |

### 核心决策原则

| 原则 | 应用 |
|------|------|
| **能用Skill解决，就不写代码** | 流程规范优先用Skill |
| **强制约束用代码，推荐规范用Skill** | 签署检查用代码，评审指南用Skill |
| **小步快跑，避免膨胀** | 版本功能控制在10-15h内 |
| **教训必须固化** | Bug和Memo结论纳入Skill |

## 跨Agent协作规范

### 独立Session Agent调用

**原则**：禁止在当前会话中用`task`唤起其他Agent

```
错误做法：
❌ task(subagent_type="general", ...) → 同一会话内嵌套，破坏独立性

正确做法：
✅ 通过外部通知，让目标Agent在独立Session自主工作
```

### 评审任务Todo机制

**需求文档完成后，交由其他Agent评审必须通过Todo机制**

```
流程：
1. 产品Agent完成需求文档自检
2. 创建Todo记录评审任务
3. 同步Todo到git
4. 通知目标Agent（在独立Session）
5. 目标Agent评审并更新Todo状态
```

### 需求文档 + 概要设计 一起评审规则 ⭐

**规则**：需求文档和概要设计必须一起评审，不允许分开评审。

```
现状问题：
├── 需求文档单独评审
├── 概要设计单独评审
└── 评审碎片化，关联性丢失

解决方案：
├── 需求文档完成后，创建"评审需求+概要设计"Todo
├── Agent 2 一起评审两个文档
└── 签署时两个文档一起签署
```

**Todo内容模板**：
```
Agent2评审 vX.X.X 需求文档 + 概要设计

参考文档：
- docs/01-requirements/requirements_vX.X.X.md
- docs/02-design/OUTLINE_vX.X.X.md
```

### Todo创建范围规范

**原则**：Todo只跟踪"本Session能完成的工作"

```
当前阶段：需求评审
→ Todo内容："Agent2评审vX.X.X需求文档并签署"
→ 不包含：设计、开发、测试等后续阶段工作

后续阶段：由负责该阶段的Agent创建新Todo
```

### Git同步规范

| 场景 | 是否同步 | 说明 |
|------|----------|------|
| 创建新需求文档 | ✅ | 每次正式版本更新后立即同步 |
| 需求文档版本迭代 | ✅ | v1→v2→v3每次版本更新后同步 |
| 创建评审Todo | ✅ | 形成正式任务后同步 |
| 自检修复未形成版本 | ❌ | 合并到下一版本后同步 |
| 草稿阶段文档 | ❌ | 状态为DRAFT时不需同步 |

如果本版本有推迟功能：

1. 创建 `PARKED_vX.X.X_features.md`
2. 记录：
   - 功能名称和来源
   - 推迟原因
   - 原始验收标准
   - 后续建议版本
   - 相关文档路径

## 常见问题

### Q: 验收标准要写多少项？

A: 每个功能至少 3-5 项验收标准，覆盖正常流程和异常流程。

### Q: 工时预估不准怎么办？

A: 
- 首次实现：按估算工时的 1.5-2 倍计算
- 复用的功能：按估算的 0.5-0.75 倍计算
- 复杂功能：拆分为多个小版本

### Q: 漏了章节怎么办？

A: 运行检查脚本 `./scripts/check_requirements.sh`，会自动检测缺失章节。

## 版本结束后需求分析环节 ⭐ (v2.2.5 起生效)

**每个版本部署完成后，必须立即执行需求分析**

### 触发条件

```
版本部署完成 (deployment.status: completed)
    ↓
立即启动"版本结束后需求分析"
```

### 分析范围

| 文档类型 | 说明 | 处理方式 |
|----------|------|----------|
| Proposal | 所有待处理的提案 | 纳入需求分析 |
| Retrospective | 版本回顾文档 | 纳入需求分析 |
| Memo | 备忘录、教训总结 | 纳入需求分析 |
| Bug Report | Bug处理意见 | 纳入需求分析 |
| Strategic Plan | 战略规划 | 纳入需求分析 |

### 输出

```
版本结束后需求分析报告
    ↓
确定下一版本功能范围
    ↓
创建需求文档 → 进入评审流程
```

### 与正常需求分析的区别

| 维度 | 正常需求分析 | 版本结束后需求分析 |
|------|-------------|-------------------|
| 触发时机 | 随时 | 版本部署完成后立即 |
| 分析范围 | 新需求 | 所有待处理文档 |
| 强制执行 | 可选 | **必须** |
| 产出 | 单个需求决策 | 下一版本完整范围 |

### 版本周期规则 ⭐

**规则**：做完一期 → 重新需求分析 → 调整排期 → 做当期需求文档

| 阶段 | 操作 | 说明 |
|------|------|------|
| 1 | 版本部署完成 | deployment.status: completed |
| 2 | 重新需求分析 | 收集所有待处理文档 |
| 3 | 调整排期 | 确定下一版本范围 |
| 4 | 做当期需求文档 | 只做当前版本的需求文档 |
| **禁止** | 跨期做需求文档 | 不要同时规划 v2.2.5 和 v2.2.6 |

**核心原则**：
- 每期交付物清晰
- 避免需求蔓延
- 保持节奏可控
- 稳步推进
