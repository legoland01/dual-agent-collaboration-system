# OC-Collab 需求编写指南

## 快速开始

### 创建新需求文档

```bash
# 1. 先做需求分析
#    分析所有历史文档，识别可用Skill解决的问题
#    分析结果输出到 ANALYSIS_vX.X.X_Requirements_Analysis.md

# 2. 复制模板
cp docs/01-requirements/TEMPLATE_requirements.md docs/01-requirements/requirements_vX.X.X_DRAFT.md

# 3. 编辑文档
#    - 填写所有必须字段
#    - 明确验收标准
#    - 预估工时

# 4. 状态流转
#    DRAFT → READY (产品完成) → APPROVED (开发确认)
```

## 需求分析环节 ⭐

**创建需求文档前，必须先做需求分析**

```
提案 → 需求分析 ← 分析所有历史文档
     ↓
  需求文档 → 设计 → 开发 → 测试 → 验收
```

### 为什么要做需求分析？

| 原因 | 说明 |
|------|------|
| 避免重复造轮子 | 先查历史，避免重复实现已有功能 |
| 识别Skill机会 | 80%流程问题可用Skill低成本解决 |
| 明确开发范围 | 区分必须代码实现 vs 可用Skill替代 |
| 吸取历史教训 | 分析Bug、Memo避免重复踩坑 |

### 需求分析步骤

```bash
# 步骤1: 收集相关文档
ls docs/01-requirements/PROPOSAL*.md   # 提案
ls docs/00-memos/MEMO*.md               # 备忘录
ls docs/00-memos/BUG*.md                # Bug报告
ls skills/*.md                          # 现有Skill

# 步骤2: 分析每个问题/需求
#    - 问题来源？根本原因？
#    - 可否用Skill解决？
#    - 是否必须代码实现？

# 步骤3: 分类决策
#    ┌─────────────────────────────────────────┐
#    │ 决策类型                                  │
#    ├─────────────────────────────────────────┤
#    │ ✅ 用Skill：无需代码，编写/更新Skill      │
#    │ 💻 纳代码：必须CLI实现，纳入开发版本      │
#    │ ⏸️ 推迟：优先级低，推迟到后续版本         │
#    │ ❌ 放弃：不适合或已过时                  │
#    └─────────────────────────────────────────┘

# 步骤4: 输出分析报告
docs/01-requirements/ANALYSIS_vX.X.X_Requirements_Analysis.md
```

### 需求分析报告模板

```markdown
# vX.X.X 需求分析报告

## 一、分析方法论

### 1.1 分析范围
本报告基于对以下文档的分析：
- Proposal（提案）：X个
- Memo（备忘录）：X个
- Bug Report（Bug报告）：X个
- Skill（技能指南）：X个

### 1.2 分析框架

| 维度 | 说明 |
|------|------|
| 问题来源 | 从哪个文档发现问题/需求原因 | 问题 |
| 根本背后的深层原因 |
| 解决方案 | Skill vs 代码实现 |
| 优先级 | P0/P1/P2 |
| 决策 | 用Skill/纳代码/推迟/放弃 |

## 二、问题与需求清单

| 编号 | 问题/需求 | 来源 | 决策 | 类型 |
|------|-----------|------|------|------|
| Q-001 | xxx | PROPOSAL_xxx | 用Skill | Skill |
| Q-002 | xxx | MEMO_xxx | 纳代码 | 代码 |
| Q-003 | xxx | BUG_xxx | 推迟 | - |

## 三、解决方案分类

### 3.1 用Skill实现（无需代码开发）
| 编号 | 功能 | 现有Skill | 状态 |
|------|------|----------|------|
| S-001 | xxx | oc_collab_xxx_guide | 已覆盖 |

### 3.2 纳入vX.X.X（需要代码实现）
| 编号 | 功能 | 工时 | 优先级 |
|------|------|------|--------|
| C-001 | xxx | Xh | P0 |

### 3.3 推迟
| 编号 | 功能 | 原因 |
|------|------|------|
| D-001 | xxx | 优先级低 |

## 四、vX.X.X 范围定义

### 版本目标
...

### 功能清单
...

## 五、决策依据
...
```

### 历史文档分析清单

| 文档类型 | 检查重点 |
|----------|----------|
| **Proposal** | 功能需求、解决方案、工时预估 |
| **Memo** | 根本问题分析、教训总结 |
| **Bug Report** | 已发现问题、系统缺陷 |
| **Skill** | 现有流程规范、已覆盖场景 |
| **Meeting Notes** | 协作流程、决策记录 |

### 核心决策原则

| 原则 | 应用 |
|------|------|
| **能用Skill解决，就不写代码** | 流程规范优先用Skill |
| **强制约束用代码，推荐规范用Skill** | 签署检查用代码，评审指南用Skill |
| **小步快跑，避免膨胀** | 版本功能控制在10-15h内 |
| **教训必须固化** | Bug和Memo结论纳入Skill |

## 跨Agent协作规范

### 独立Session Agent调用

**原则**：禁止在当前会话中用`task`唤起其他Agent

```
错误做法：
❌ task(subagent_type="general", ...) → 同一会话内嵌套，破坏独立性

正确做法：
✅ 通过外部通知，让目标Agent在独立Session自主工作
```

### 评审任务Todo机制

**需求文档完成后，交由其他Agent评审必须通过Todo机制**

```
流程：
1. 产品Agent完成需求文档自检
2. 创建Todo记录评审任务
3. 同步Todo到git
4. 通知目标Agent（在独立Session）
5. 目标Agent评审并更新Todo状态
```

### Todo创建范围规范

**原则**：Todo只跟踪"本Session能完成的工作"

```
当前阶段：需求评审
→ Todo内容："Agent2评审vX.X.X需求文档并签署"
→ 不包含：设计、开发、测试等后续阶段工作

后续阶段：由负责该阶段的Agent创建新Todo
```

### Git同步规范

| 场景 | 是否同步 | 说明 |
|------|----------|------|
| 创建新需求文档 | ✅ | 每次正式版本更新后立即同步 |
| 需求文档版本迭代 | ✅ | v1→v2→v3每次版本更新后同步 |
| 创建评审Todo | ✅ | 形成正式任务后同步 |
| 自检修复未形成版本 | ❌ | 合并到下一版本后同步 |
| 草稿阶段文档 | ❌ | 状态为DRAFT时不需同步 |

## 双签流程

### 签署顺序

| 步骤 | 签署人 | 说明 |
|------|--------|------|
| 1 | Agent 1 | 产品负责人创建并签署 |
| 2 | Agent 2 | 开发负责人评审并签署 |

### 签署状态

| 状态 | 说明 |
|------|------|
| DRAFT | 草稿（产品编写中） |
| READY | 就绪（待开发评审） |
| APPROVED | 批准（可开始开发） |

## 推迟功能处理

如果本版本有推迟功能：

1. 创建 `PARKED_vX.X.X_features.md`
2. 记录：
   - 功能名称和来源
   - 推迟原因
   - 原始验收标准
   - 后续建议版本
   - 相关文档路径

## 常见问题

### Q: 验收标准要写多少项？

A: 每个功能至少 3-5 项验收标准，覆盖正常流程和异常流程。

### Q: 工时预估不准怎么办？

A: 
- 首次实现：按估算工时的 1.5-2 倍计算
- 复用的功能：按估算的 0.5-0.75 倍计算
- 复杂功能：拆分为多个小版本

### Q: 漏了章节怎么办？

A: 运行检查脚本 `./scripts/check_requirements.sh`，会自动检测缺失章节。
