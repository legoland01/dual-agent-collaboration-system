## 需求分析环节 ⭐

**创建需求文档前，必须先做需求分析**

**核心原则**：所有进入需求文档的功能，**必须经过需求分析**。

```
需求来源
    │
    ├── Proposal ──→ 需求分析 ──┐
    │                          │
    ├── Memo ───────→ 需求分析 ──┼──→ 分类决策
    │                          │
    ├── Bug Report ──→ 需求分析 ──┤
    │                          │
    └── 其他 ────────→ 需求分析 ──┘
                              │
                    ┌─────────┴─────────┐
                    │                   │
               ┌────▼────┐         ┌────▼────┐
               │ 用Skill │         │ 需开发  │
               └─────────┘         └────┬────┘
                                         │
                                   创建需求文档 ✅
                                   (需要评审)
```

**关键规则**：
| 规则 | 说明 |
|------|------|
| 需求必须来源 | 需求文档中的需求必须来自需求分析 |
| 禁止直接添加 | 不能跳过需求分析直接创建需求文档 |
| 入口唯一 | 需求分析是进入需求文档的唯一入口 |

### 为什么要做需求分析？

| 原因 | 说明 |
|------|------|
| 避免重复造轮子 | 先查历史，避免重复实现已有功能 |
| 识别Skill机会 | 80%流程问题可用Skill低成本解决 |
| 明确开发范围 | 区分必须代码实现 vs 可用Skill替代 |
| 吸取历史教训 | 分析Bug、Memo避免重复踩坑 |

### 核心概念澄清

| 概念 | 说明 | 是否需要评审 |
|------|------|--------------|
| **Proposal** | 解决方案建议 | ❌ 不需要 |
| **Skill** | 流程规范指南 | ❌ 不需要 |
| **需求文档** | 正式纳入版本的功能定义 | ✅ 需要评审 |
| **PARKED** | 推迟的功能 | ❌ 不需要 |

### 需求分析步骤

```bash
# 步骤1: 收集相关文档
ls docs/01-requirements/PROPOSAL*.md   # 提案
ls docs/00-memos/MEMO*.md               # 备忘录
ls docs/00-memos/BUG*.md                # Bug报告
ls skills/*.md                          # 现有Skill

# 步骤2: 分析每个问题/需求
#    - 问题来源？根本原因？
#    - 可否用Skill解决？
#    - 是否必须CLI实现？

# 步骤3: 分类决策
#    ┌─────────────────────────────────────────┐
#    │ 决策类型       │ 下一步                │ 是否评审 │
#    ├─────────────────────────────────────────┤
#    │ ✅ 用Skill   │ 编写/更新Skill文档     │  不需要  │
#    │ 💻 需开发   │ 创建需求文档          │  需要    │
#    │ ⏸️ 推迟    │ 放入PARKED            │  不需要  │
#    │ ❌ 放弃    │ 关闭Proposal          │  不需要  │
#    └─────────────────────────────────────────┘

# 步骤4: 输出分析报告
docs/01-requirements/ANALYSIS_vX.X.X_Requirements_Analysis.md
```

### 历史文档分析清单

| 文档类型 | 检查重点 |
|----------|----------|
| **Proposal** | 功能需求、解决方案、工时预估 |
| **Memo** | 根本问题分析、教训总结 |

### 核心决策原则

| 原则 | 应用 |
|------|------|
| **能用Skill解决，就不写代码** | 流程规范优先用Skill |

| **小步快跑，避免膨胀** | 版本功能控制在10-15h内 |
| **教训必须固化** | Bug和Memo结论纳入Skill |

## 跨Agent协作规范

### 独立Session Agent调用

**原则**：禁止在当前会话中用`task`唤起其他Agent

```
错误做法：
❌ task(subagent_type="general", ...) → 同一会话内嵌套，破坏独立性

正确做法：
✅ 通过外部通知，让目标Agent在独立Session自主工作
```

### 评审任务Todo机制

**需求文档完成后，交由其他Agent评审必须通过Todo机制**

```
流程：
1. 产品Agent完成需求文档自检
2. 创建Todo记录评审任务
3. 同步Todo到git
4. 通知目标Agent（在独立Session）
5. 目标Agent评审并更新Todo状态
```

### 需求文档 + 概要设计 一起评审规则 ⭐

**规则**：需求文档和概要设计必须一起评审，不允许分开评审。

```
现状问题：
├── 需求文档单独评审
├── 概要设计单独评审
└── 评审碎片化，关联性丢失

解决方案：
├── 需求文档完成后，创建"评审需求+概要设计"Todo
├── Agent 2 一起评审两个文档
└── 签署时两个文档一起签署
```

**Todo内容模板**：
```
Agent2评审 vX.X.X 需求文档 + 概要设计

参考文档：
- docs/01-requirements/requirements_vX.X.X.md
- docs/02-design/OUTLINE_vX.X.X.md
```

### Todo创建范围规范

**原则**：Todo只跟踪"本Session能完成的工作"

```
当前阶段：需求评审
→ Todo内容："Agent2评审vX.X.X需求文档并签署"
→ 不包含：设计、开发、测试等后续阶段工作

后续阶段：由负责该阶段的Agent创建新Todo
```

### Git同步规范

| 场景 | 是否同步 | 说明 |
|------|----------|------|
| 创建新需求文档 | ✅ | 每次正式版本更新后立即同步 |
| 需求文档版本迭代 | ✅ | v1→v2→v3每次版本更新后同步 |
| 创建评审Todo | ✅ | 形成正式任务后同步 |
| 自检修复未形成版本 | ❌ | 合并到下一版本后同步 |
| 草稿阶段文档 | ❌ | 状态为DRAFT时不需同步 |

## 常见问题

### Q: 验收标准要写多少项？

A: 每个功能至少 3-5 项验收标准，覆盖正常流程和异常流程。

### Q: 工时预估不准怎么办？

A: 
- 首次实现：按估算工时的 1.5-2 倍计算
- 复用的功能：按估算的 0.5-0.75 倍计算
- 复杂功能：拆分为多个小版本

### Q: 漏了章节怎么办？

A: 运行检查脚本 `./scripts/check_requirements.sh`，会自动检测缺失章节。

## 版本结束后需求分析环节 ⭐ (v2.2.5 起生效)

**每个版本部署完成后，必须立即执行需求分析**

### 触发条件

```
版本部署完成 (deployment.status: completed)
    ↓
立即启动"版本结束后需求分析"
```

### 分析范围

| 文档类型 | 说明 | 处理方式 |
|----------|------|----------|
| Proposal | 所有待处理的提案 | 纳入需求分析 |
| Retrospective | 版本回顾文档 | 纳入需求分析 |
| Memo | 备忘录、教训总结 | 纳入需求分析 |
| Bug Report | Bug处理意见 | 纳入需求分析 |
| Strategic Plan | 战略规划 | 纳入需求分析 |

### 输出

```
版本结束后需求分析报告
    ↓
确定下一版本功能范围
    ↓
创建需求文档 → 进入评审流程
```

### 与正常需求分析的区别

| 维度 | 正常需求分析 | 版本结束后需求分析 |
|------|-------------|-------------------|
| 触发时机 | 随时 | 版本部署完成后立即 |
| 分析范围 | 新需求 | 所有待处理文档 |
| 强制执行 | 可选 | **必须** |
| 产出 | 单个需求决策 | 下一版本完整范围 |

### 版本周期规则 ⭐

**规则**：做完一期 → 重新需求分析 → 调整排期 → 做当期需求文档

| 阶段 | 操作 | 说明 |
|------|------|------|
| 1 | 版本部署完成 | deployment.status: completed |
| 2 | 重新需求分析 | 收集所有待处理文档 |
| 3 | 调整排期 | 确定下一版本范围 |
| 4 | 做当期需求文档 | 只做当前版本的需求文档 |
| **禁止** | 跨期做需求文档 | 不要同时规划 v2.2.5 和 v2.2.6 |

**核心原则**：
- 每期交付物清晰
- 避免需求蔓延
- 保持节奏可控
- 稳步推进

## 八、TODO创建规则 ⭐

**基于 BUG-20260209-001 教训：不要替其他Agent分解任务**

### 黄金法则

| 规则 | 说明 | 示例 |
|------|------|------|
| **只创建当前步骤的TODO** | 只创建"下一步要做"的TODO，不要创建下下步的TODO | ✅ 修复Bug → ❌ 不要同时创建"修复后测试" |
| **不提前创建** | 只有当某项工作明确需要做时才创建TODO | ❌ Bug还没发现就创建"修复Bug的TODO" |
| **不代他人创建** | 即使TODO指向自己，也不要替别人创建 | ❌ Agent1 不要创建"Agent2修复Bug"的TODO |
| **不自创TODO** | 不要为了"可能有需要"而预先创建TODO | ❌ "以后可能需要测试" → 实际需要时再创建 |

### 创建前检查清单

```bash
# 创建TODO前必须检查：
1. ✅ 这项工作明确要做吗？
2. ✅ 这项工作现在必须做吗？
3. ✅ 这是他人的工作吗？（如果是，只有对方需要时协助创建）
4. ✅ 这项工作可能变化吗？（如果是，推迟到明确时再创建）
```

### 禁止行为

| ❌ 错误做法 | ✅ 正确做法 |
|-------------|-------------|
| 替 Agent2 分解任务 | 只创建"开发v2.2.6"TODO，让 Agent2 自己分解 |
| 提前创建"修复后测试"的TODO | 等 Agent2 修复后，Agent1 自主创建 |
| 创建大量重复TODO | 避免重复，确保每个TODO唯一 |

### 评审反馈TODO体系

**原则**：TODO是短程"通知-完成"结构，保持最大灵活性

```
Agent2评审 → TODO设为complete（评审工作完成）
              ↓
        如需Agent1反馈
              ↓
      Agent2创建新TODO给Agent1
```

**禁止**：Agent2将评审TODO设为complete后，自己再创建TODO给自己

### 实际案例

| 场景 | 错误做法 | 正确做法 |
|------|----------|----------|
| Agent2发现Bug | 创建"Agent2修复"的TODO + 提前创建"Agent1重新测试"的TODO ❌ | 只创建"Agent2修复"的TODO，Agent1看到修复后自主创建测试TODO ✅ |
| Agent1提交需求 | 替Agent2创建开发TODO ❌ | 创建"评审需求"TODO，让Agent2决定如何分解 ✅ |

### 开发TODO创建规则 ⭐ (BUG-20260214-002补充)

**规则**：设计阶段完成后，Agent1必须创建开发TODO给Agent2。

| 阶段 | TODO创建者 | TODO类型 | 示例 |
|------|-----------|----------|------|
| 需求评审 | Agent1 | 评审TODO | "Agent2评审需求文档" |
| 设计评审 | Agent1 | 评审TODO | "Agent2评审详细设计" |
| **开发阶段** | **Agent1** | **开发TODO** | "Agent2实现StateNotifier集成" |

**示例**：
```
正确做法：
oc-collab todowrite --content "实现v2.2.9功能：StateNotifier集成todowrite" --priority high --agent 2

错误做法：
- Agent2自己创建开发TODO给自己 ❌
- Agent1不创建开发TODO给Agent2 ❌
```

**原理**：
- Agent1把控需求和设计，清楚功能范围
- Agent2基于TODO执行开发，不需要自己分解任务
- 避免Agent2自己给自己创建TODO（违反职责边界）

---

**核心原则**：
- 保持TODO精简
- 尊重Agent职责边界
- 避免提前预测需求

## 九、历史推迟功能分析 ⭐ (v1.0.8起生效)

**每次需求分析必须检查历史推迟功能**

### 9.1 触发条件

```
每次需求分析（版本结束后或新功能）
    ↓
必须检查：
    1. 历史上推迟>=4次的功能
    2. 与现有功能的关系（重叠/替代/独立）
    3. 被放弃的原因
```

### 9.2 分析步骤

```bash
# 步骤1: 收集历史推迟功能
ls docs/01-requirements/PARKED_*.md          # 推迟功能池
cat docs/01-requirements/HISTORY_POSTPONED_FEATURES_ANALYSIS.md  # 综合分析

# 步骤2: 检查与现有功能的关系
#    ┌─────────────────────────────────────────────┐
#    │ 历史功能 vs 现有功能                       │
#    ├─────────────────────────────────────────────┤
#    │ 重叠    │ 合并或取消一个                   │
#    │ 替代    │ 用现有功能替代                   │
#    │ 独立    │ 保持独立，可推迟                 │
#    └─────────────────────────────────────────────┘

# 步骤3: 明确放弃原因
#    ┌─────────────────────────────────────────────┐
#    │ 放弃原因分类                               │
#    ├─────────────────────────────────────────────┤
#    │ 太复杂    │ 需要重构                       │
#    │ 非核心    │ 不是CLI核心功能                 │
#    │ 可选      │ 优先级低                       │
#    │ 需先定规范│ 依赖其他规范定义               │
#    │ 高风险    │ 迁移风险高                     │
#    │ 已替代    │ 已有功能替代                   │
#    └─────────────────────────────────────────────┘

# 步骤4: 输出分析报告
docs/01-requirements/HISTORY_POSTPONED_FEATURES_ANALYSIS.md
```

## 十、Proposal收集与处理 ⭐ (v1.0.9起生效)

**每次需求分析必须收集和处理Proposal**

### 10.1 Proposal收集

```bash
# 步骤1: 收集所有待处理Proposal
ls docs/04-proposals/PROPOSAL-*.md

# 步骤2: 分类Proposal
#    ┌─────────────────────────────────────┐
#    │ Proposal类型                         │
#    ├─────────────────────────────────────┤
#    │ 新功能    │ 已有功能增强              │
#    │ 优化      │ Bug修复                  │
#    │ 重构      │ 基础设施改进             │
#    └─────────────────────────────────────┘
```

### 10.2 Proposal处理流程

```
收到Proposal
    │
    ├── 验证Proposal格式
    │       ├── 必需字段：编号、日期、状态、优先级
    │       └── 必需字段：关联BUG、来源
    │
    ├── 分析Proposal价值
    │       ├── P0 - 核心痛点，立即处理
    │       ├── P1 - 重要功能，下版本处理
    │       └── P2 - 可选功能，推迟
    │
    ├── 确定分期
    │       ├── 纳入当前版本
    │       ├── 纳入后续版本（指定版本号）
    │       ├── 放入PARKED（推迟）
    │       └── 放弃（明确原因）
    │
    └── 更新Proposal状态
            └── 标记版本号或放弃原因
```

### 10.3 Proposal分期规则

| 规则 | 说明 |
|------|------|
| **P0立即处理** | 核心痛点，纳入当前版本 |
| **P1规划处理** | 重要功能，纳入后续版本（v2.x） |
| **P2可选处理** | 低优先级，放入PARKED |
| **反复推迟** | 连续4次推迟，必须评估是否真正需要 |
| **功能重叠** | 与现有功能重叠，合并或取消 |

### 10.4 对Proposal的要求

| 字段 | 必需 | 说明 |
|------|------|------|
| 编号 | ✅ | PROPOSAL-YYYY-MM-XXX |
| 状态 | ✅ | DRAFT / READY / APPROVED / REJECTED |
| 优先级 | ✅ | P0 / P1 / P2 |
| 来源 | ✅ | 来源文档或问题 |
| 工时 | ✅ | 预估工时 |
| 依赖 | ✅ | 依赖的其他功能 |
| 验收标准 | ✅ | 可验证的验收标准 |

### 10.5 每周期主题选择

**每个需求分析周期可以选择一个主题深入讨论**

```
主题选择原则：
├── 当前版本痛点 → 优先解决
├── 历史积压 → 优先处理
├── 技术债务 → 周期性清理
└── 新技术探索 → 可选

主题选择示例：
├── 主题：CLI工具完善 → 聚焦CLI相关Proposal
├── 主题：Skill体系 → 聚焦Skill相关Proposal
├── 主题：通知机制 → StateNotifier相关Proposal
└── 主题：质量保证 → 测试覆盖率相关Proposal
```

### 10.6 Proposal状态流转

```
DRAFT (草稿)
    │
    ├── Agent1完成
    └── READY (就绪)

READY (就绪)
    │
    ├── Agent2评审通过
    │       └── APPROVED (批准)
    │
    ├── Agent2评审有异议
    │       └── 返回修改 或 REJECTED
    │
    └── 延期处理
            └── 放入PARKED

APPROVED (批准)
    │
    └── 纳入版本规划
            ├── 纳入当前版本
            └── 纳入后续版本

REJECTED (拒绝)
    │
    └── 记录原因，关闭Proposal

PARKED (推迟)
    │
    ├── 后续版本实现
    │       └── 移出PARKED
    │
    └── 放弃
            └── 关闭Proposal
```

### 10.7 强制要求

| 要求 | 说明 |
|------|------|
| **必须收集** | 每次需求分析必须收集所有待处理Proposal |
| **必须分期** | 每个Proposal必须有明确的版本归属 |
| **必须验证** | Proposal必须包含必需字段 |
| **必须闭环** | 被拒绝/放弃的Proposal必须记录原因 |

### 10.8 验收标准

| 标准 | 检查方法 |
|------|----------|
| Proposal已收集 | ls docs/04-proposals/PROPOSAL-*.md |
| 每个Proposal有分期 | Proposal标记版本号或PARKED |
| 拒绝/放弃有原因 | Proposal头部有reject_reason或parked_reason |
| 主题选择记录 | 需求分析报告有本周期主题说明 |
