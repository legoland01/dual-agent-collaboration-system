# OC-Collab 需求评审指南

## 快速参考

### 角色分工

| 角色 | 必须做 | 禁止做 |
|------|--------|--------|
| **Agent 1** | 需求文档、黑盒测试、验收签署 | 设计文档、代码、签署"评审通过" |
| **Agent 2** | 评审、设计文档、代码、白盒测试 | 黑盒测试、签署"创建需求" |

### 实质性评审

**禁止只写"✅ 通过"**，必须回答：

1. **技术可行性** - 能实现吗？有风险吗？
2. **完整性** - 验收标准可测试吗？异常流程呢？
3. **可实施性** - 工时合理吗？依赖正确吗？
4. **逆向思考** - 如果我是用户，好用吗？最大风险是什么？

---

## 评审输出模板

```
评审结果: ✅ 通过（带具体意见）

技术可行性:
- 实现方案可行
- ⚠️ 建议: xxx

完整性:
- 验收标准完整
- ✅ 已覆盖正常和异常流程

可实施性:
- 工时合理
- 无额外依赖

逆向意见:
- xxx
```

---

## 签署规范

| 角色 | 正确的签署内容 |
|------|---------------|
| Agent 1 | "创建需求" / "发起评审" |
| Agent 2 | "技术评审通过" |

---

## 常见错误

| 错误 | 正确做法 |
|------|---------|
| Agent 1 签署"评审通过" | Agent 2 签署"技术评审通过" |
| Agent 1 创建设计文档 | Agent 2 创建设计文档 |
| 评审只写"✅ 通过" | 必须提供具体意见 |

---

## Git 提交规范 ⭐

**创建或修改文档后，必须立即提交到 Git**

```bash
# 1. 创建/修改文档后，立即提交
git add docs/
git commit -m "feat: 创建/更新需求文档"

# 2. 评审通过后，提交签署状态
git add docs/
git commit -m "docs: 更新需求签署状态"
```

**禁止**: 创建文档后不提交，积压多个提交
