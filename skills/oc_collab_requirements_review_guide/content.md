# OC-Collab 需求评审指南

## 快速参考

### 角色分工

| 角色 | 必须做 | 禁止做 |
|------|--------|--------|
| **Agent 1** | 需求文档、黑盒测试、验收签署 | 设计文档、代码、签署"评审通过" |
| **Agent 2** | 评审、设计文档、代码、白盒测试 | 黑盒测试、签署"创建需求" |

---

## 7个评审视角 ⭐

评审时必须从以下7个视角检查：

| # | 视角 | 检查点 |
|---|------|--------|
| 1 | **阅读理解** | 是否正确理解需求意图 |
| 2 | **完整性** | 验收标准是否覆盖正常+异常流程 |
| 3 | **一致性** | 与现有体系是否冲突 |
| 4 | **可测试性** | 验收标准是否可验证 |
| 5 | **可行性** | 技术能否实现，有无风险 |
| 6 | **逆向挑刺** | 如果我要否定，能找到什么理由 |
| 7 | **给出结论** | 通过/不通过 + 修改建议 |

### 逆向挑刺的提问方式

- 这个需求解决了什么问题？不解决会怎样？
- 是否有更低成本的替代方案？
- 实现后可能带来什么副作用？
- 边界情况是否都考虑到了？

---

## 实质性评审

**禁止只写"✅ 通过"**，必须回答：

1. **技术可行性** - 能实现吗？有风险吗？
2. **完整性** - 验收标准可测试吗？异常流程呢？
3. **可实施性** - 工时合理吗？依赖正确吗？
4. **逆向思考** - 如果我是用户，好用吗？最大风险是什么？

---

## 评审输出模板

按照7个视角逐项输出：

```
评审结论: ✅ 通过（带具体意见）

1. 阅读理解:
- 正确理解需求意图
- ⚠️ 建议: xxx

2. 完整性:
- 验收标准覆盖正常+异常流程
- ✅ 已覆盖 / ❌ 缺失异常流程

3. 一致性:
- 与现有体系无冲突
- ✅ 已覆盖 / ❌ 存在冲突

4. 可测试性:
- 验收标准可验证
- ✅ 已覆盖 / ❌ 需补充

5. 可行性:
- 技术方案可行
- ⚠️ 风险: xxx

6. 逆向挑刺:
- 潜在问题: xxx
- 替代方案: xxx

7. 评审结论:
- ✅ 通过
- 或 ❌ 不通过 + 修改建议
```

## 签署规范

| 角色 | 正确的签署内容 |
|------|---------------|
| Agent 1 | "创建需求" / "发起评审" |
| Agent 2 | "技术评审通过" / "技术评审通过（有条件）" |

### 有条件通过的签署

当Agent2评审有保留意见时：

| 签署内容 | 说明 |
|----------|------|
| "技术评审通过（有条件）" | 需Agent1修复问题后签署确认 |
| "技术评审通过" | 无保留意见，直接通过 |

---

## 评审反馈TODO体系 ⭐

**原则**：TODO是短程"通知-完成"结构，保持最大灵活性

### 评审后操作流程

```
Agent2评审 → 签署"技术评审通过（有条件）" 
              ↓
        将评审TODO设为complete
              ↓
        如需Agent1修复意见
              ↓
    Agent2创建新TODO给Agent1（agent_id: "1"）
```

### 禁止行为

| 禁止 | 说明 |
|------|------|
| Agent2将评审TODO设为complete后，自己再创建TODO给自己 | 必须将TODO创建给正确的执行人 |
| Agent1自己创建TODO要求自己修复 | Agent2应创建TODO给Agent1 |

### 示例

**场景**：Agent2评审发现FR-GIT-002紧急情况定义不明确

```
Agent2操作：
1. 签署："技术评审通过（有条件）"
2. 评审TODO设为complete
3. 创建新TODO：
   - id: TODO-XXX
   - content: "修复FR-GIT-002紧急情况定义"
   - agent_id: "1"
   - status: pending
```

**Agent1修复后**：
- 更新文档版本（v3→v4）
- 在签署表格中添加"修复评审意见"行
- 状态保持APPROVED

## Git 提交规范 ⭐

**创建或修改文档后，必须立即提交到 Git**

```bash
# 1. 创建/修改文档后，立即提交
git add docs/
git commit -m "feat: 创建/更新需求文档"

# 2. 推送到所有远程（GitHub + Gitee）
oc-collab sync-all -m "feat: 创建/更新需求文档"

# 3. 评审通过后，提交签署状态
git add docs/
git commit -m "docs: 更新需求签署状态"

# 4. 推送签署状态
oc-collab sync-all -m "docs: 更新需求签署状态"
```

**禁止**: 创建文档后不提交，积压多个提交
