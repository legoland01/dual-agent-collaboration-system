
## 概要设计 vs 详细设计

| 维度 | 概要设计 | 详细设计 |
|------|----------|----------|
| 视角 | 用户/功能 | 技术/代码 |
| 抽象级别 | 高（What） | 低（How） |
| 责任人 | Agent 1 | Agent 2 |
| 关注点 | 功能模块、分组、关系 | 技术模块、代码实现 |
| 与产品关系 | 直接对应 | 间接映射 |

## 核心原则

### 1. 功能模块 → 技术模块映射

**原则**：将概要设计中的功能模块映射为技术实现

```
概要设计：
- 功能模块：需求管理
- 子功能：需求创建、需求评审

详细设计：
- 技术模块：RequirementManager
- 代码类：Requirement, RequirementService
- CLI命令：oc-collab requirement create, oc-collab requirement review
```

### 2. 技术选型依据

| 选型 | 依据 | 参考 |
|------|------|------|
| Python Click | CLI框架 | 项目技术栈 |
| PyYAML | 配置解析 | 现有依赖 |
| GitPython | Git操作 | 现有依赖 |

### 3. 代码级设计

详细设计必须包含：

| 设计项 | 说明 | 详细程度 |
|--------|------|----------|
| 类设计 | 类名、属性、方法签名 | 具体实现 |
| 接口设计 | 函数签名、参数、返回值 | 具体定义 |
| 数据结构 | JSON/YAML结构 | 完整Schema |
| 异常处理 | 异常类型、错误码 | 完整列表 |
| 测试策略 | 单元测试、E2E测试 | 关键场景 |

### 4. 与概要设计的追溯

详细设计必须引用概要设计：

## 评审意见处理规则 ⭐

### 收到评审意见后的处理流程

当Agent2收到Agent1的评审意见后，必须遵循以下流程：

```
Agent1提出评审意见
        ↓
Agent2评估意见（是否合理、是否需要修改）
        ↓
根据评估结果处理：
  ├─ 合理 → 修改设计 → 提交新版本(vN+1)
  └─ 有异议 → 回复说明 → 继续讨论
        ↓
重新提交评审
```

### 处理规则

| 情况 | 处理方式 | 操作 |
|------|----------|------|
| 意见合理，需修改 | 修改设计 | 1. 更新文档版本号 (v1 → v2)<br>2. 逐条回复意见<br>3. 修改对应章节<br>4. 提交评审 |
| 意见有异议 | 回复说明 | 1. 清晰解释设计理由<br>2. 提供替代方案<br>3. 等待Agent1确认 |
| 意见模糊 | 澄清确认 | 1. 提问明确化<br>2. 确认修改方向 |

### 评审意见回复模板

每次收到评审意见后，必须在文档中回复：

```markdown
## 评审意见回复

### Agent1意见 1: [意见标题]

**Agent1**: [原文引用]

**Agent2处理**:
- ✅ 接受 / ❌ 异议

**处理说明**:
> [逐条回复]

**修改位置**:
- 章节: 3.1 类设计
- 行号: ~120行
- 修改内容: [简述修改]
```

### 版本号管理规则

| 轮次 | 版本号 | 说明 |
|------|--------|------|
| 首次提交 | v1 | 初始版本 |
| 第1次修改后 | v2 | Agent1意见修改 |
| 第2次修改后 | v3 | 继续迭代 |
| ... | vN | 继续迭代 |

**规则**:
- 每次修改必须+1版本号
- 修改前备份当前版本
- 修改后标注"vN 已修改"

### 禁止行为

| ❌ 禁止 | 说明 |
|---------|------|
| 不回复意见直接修改 | 每条意见必须明确回复 |
| 大幅修改后不更新版本号 | 无法追踪修改历史 |
| 合并多条意见一起处理 | 应逐条回复 |
| 跳过评审直接进入开发 | 必须等Agent1签署 |

### 快速处理清单

收到评审意见后：

- [ ] 逐条阅读意见，理解意图
- [ ] 评估意见合理性
- [ ] 确定修改范围
- [ ] 更新版本号
- [ ] 逐条回复意见
- [ ] 执行修改
- [ ] 提交新版本评审

## 多次评审规则 ⭐

### 背景

详细设计可能需要多次评审迭代，本章节明确评审规则。

### 1. 评审状态流转

```
DRAFT → REVIEW_PENDING (Agent2提交评审)
REVIEW_PENDING → APPROVED (评审通过)
REVIEW_PENDING → DRAFT (需修改，Agent2重新提交)
```

### 2. 迭代评审流程

| 轮次 | 触发条件 | 操作 |
|------|----------|------|
| 第1轮 | 首次提交 | Agent1评审 |
| 第2轮 | 首次不通过 | Agent2修改后提交v2 |
| 第3轮+ | 继续迭代 | 每次迭代+1版本号 |

**规则**:
- 每次迭代必须更新文档版本号 (v1 → v2 → v3...)
- 评审不通过需明确指出问题
- 修改后重新提交视为新版本

### 3. 评审通过条件

| 角色 | 签署内容 | 说明 |
|------|----------|------|
| Agent 1 | "创建" | 首次创建详细设计 |
| Agent 1 | "确认修改" | 确认Agent2的修改满足要求 |
| Agent 2 | "技术评审通过" | 技术实现可行 |

**完整通过条件**:
1. Agent1 签署 "创建" 或 "确认修改"
2. Agent2 签署 "技术评审通过"
3. 文档状态更新为 APPROVED

### 4. 版本号管理

| 版本 | 触发 | 版本号规则 |
|------|------|------------|
| v1 | 首次创建 | 初始版本 |
| v2 | 首次修改后 | 首次评审不通过后的修改 |
| v3... | 继续迭代 | 每次修改+1 |

### 6. 禁止行为

| 角色 | 禁止行为 |
|------|----------|
| Agent 1 | 签署"技术评审通过"（只能签署产品相关内容） |
