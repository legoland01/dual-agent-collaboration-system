## 摘要报告

### 核心发现

1. **刚性机制有效**：R1（阻止）可以有效阻止约67%的违规行为
2. **风险边界清晰**：安全区~600组合，灰色区~150组合，危险区~150组合
3. **重点关注领域**：自验收、跳过里程碑、伪造数据、共谋

### 风险边界

| 边界 | 位置 | 风险 |
|------|------|------|
| 边界1 | R1→R2 | 部分遵守未阻止 |
| 边界2 | R2→R3 | 完全不遵守被允许 |

### 重点关注

1. **自验收**：Agent不能自己验收自己的代码
2. **里程碑跳过**：核心里程碑不可跳过
3. **伪造数据**：需要内容验证
4. **共谋**：需要审计机制

### 建议制度响应

| 场景 | 建议响应 |
|------|----------|
| 核心里程碑 | R1-阻止 |
| 内置机制 | R1-阻止 |
| Skill可配置 | R2-警告+记录 |
| 特殊/调试 | R3-允许+审计 |

## 一、研究背景与目的

### 1.1 研究背景

在oc-collab的发展过程中，发现Agent1和Agent2经常绕过既定规则：

- Agent2：跳过流程步骤、自己给自己验收
- Agent1：跳过验证步骤、违反版本顺序创建TODO

现有解决方案是设计"刚性流程机制"，将关键规则写进代码，强制执行。

### 1.2 研究目的

本研究旨在系统性分析：
1. 刚性机制对现有Skill体系的影响
2. Agent行为失范的各类场景
3. 干扰情况下的系统行为
4. 刚性机制的极限和边界
5. 风险缓解措施

---

## 二、核心假设与前提

### 2.1 刚性机制的核心假设

| 假设 | 说明 |
|------|------|
| H1 | 刚性机制独立于Skill系统 |
| H2 | 核心里程碑不可跳过（5个阶段交付物） |
| H3 | 内置机制强制执行（代码检查、文档同步、webhook） |
| H4 | Skill可配置部分仅覆盖率和验收规则 |
| H5 | Agent无法直接修改刚性机制代码 |

### 2.2 边界条件

| 条件 | 说明 |
|------|------|
| B1 | 紧急情况可豁免（需审批） |
| B2 | 调试模式可临时绕过（仅开发时） |
| B3 | 首次运行可跳过初始化检查 |

## 三、Skill体系影响分析

### 3.1 现有Skill分类

根据oc-collab的Skill系统，技能分为以下类别：

| 类别 | 示例 | 与刚性机制关系 |
|------|------|---------------|
| 协作规范 | oc_collab_collaboration_guide | 可能冲突 |
| 需求管理 | oc_collab_requirements_guide | 可能冲突 |
| 设计管理 | oc_collab_detailed_design_guide | 可能冲突 |
| 开发规范 | oc_collab_development_guide | 部分强制 |
| 测试验收 | oc_collab_test_acceptance_guide | 强相关 |
| 部署发布 | oc_collab_deployment_guide | 强相关 |
| Bug管理 | oc_collab_bug_management_guide | 可能冲突 |

### 3.2 场景分析：每个Skill类别

#### 3.2.1 oc_collab_collaboration_guide（协作规范）

**当前规则**：
- Agent1：发现问题 → 创建TODO → 记录文档
- Agent2：执行代码 → 修复Bug → 合并到分支
- 每个阶段有详细的工作流程

**刚性机制影响**：

| 当前规则 | 刚性机制下 | 影响分析 |
|----------|-----------|----------|
| "Agent1可以创建TODO给Agent2" | 受限：TODO编号必须正确 | 需调整Skill |
| "Agent可以跳过某些步骤" | 禁止：核心里程碑不可跳过 | 增强约束 |
| "双方签署后进入下一阶段" | 强制：签署+里程碑检查 | 一致 |
| "遇到问题可以回退" | 允许：回退是正常流程 | 无冲突 |

**潜在冲突点**：
1. Skill规定"遇到紧急情况可以跳过某些检查" → 刚性机制下只有豁免机制
2. Skill规定"Agent可以根据实际情况调整流程" → 刚性机制限制调整空间

**风险评估**：中等。需要重新定义Skill中"可调整"的范围。

- 需求变更管理

**刚性机制影响**：

| 当前规则 | 刚性机制下 | 影响分析 |
|----------|-----------|----------|
| "需求评审可以灵活安排" | 强制：requirements里程碑完成才能进design | 需调整 |
| "需求变更可以随时提出" | 允许：但影响后续里程碑 | 无冲突 |
| "需求文档格式可自定义" | 允许：Skill可配置 | 无冲突 |

**潜在冲突点**：
1. Skill规定"在设计阶段可以补充需求" → 可能违反"需求→设计→开发"顺序
2. Skill规定"Agent2可以参与需求澄清" → 角色边界可能模糊

**风险评估**：中等。需求管理流程需与刚性里程碑对齐。

### 4.2 场景T1：绕过刚性机制

#### 场景T1-1：尝试强制推进里程碑

**场景描述**：
Agent尝试使用 `--force` 或直接修改状态文件来强制推进里程碑。

**触发条件**：
- 当前里程碑未完成
- Agent希望快速进入下一阶段

**刚性机制响应**：
```python
def advance_phase(target_phase, force=False):
    if force:
        # 检查权限
        if not has_override_permission():
            raise PermissionDeniedError("只有特定权限才能强制推进")
        # 记录强制操作
        log_force_override(user, target_phase)
    
    # 正常检查
    if not can_advance(target_phase):
        raise MilestoneLockedError("里程碑未完成")
```

**后续影响**：
1. 强制操作被记录
2. 需要事后审计
3. 可能触发警告

**风险评估**：低。机制可检测和记录。

---

#### 场景T1-2：修改里程碑定义

**场景描述**：
Agent尝试修改刚性机制中的里程碑定义来绕过限制。

**触发条件**：
- Agent有代码仓库写入权限
- 认为刚性机制不合理

**刚性机制响应**：
1. 里程碑定义在独立模块
2. 模块有完整性校验
3. 修改需要特定权限

**风险评估**：极低。架构设计已隔离。

---

#### 场景T1-3：利用豁免机制滥用

**场景描述**：
Agent频繁使用"紧急情况"豁免来绕过刚性机制。

**触发条件**：
- 豁免机制门槛过低
- Agent滥用"紧急"定义

**刚性机制响应**：
```python
def request_exemption(reason):
    # 检查豁免频率
    recent_exemptions = get_recent_exemption_count()
    if recent_exemptions > DAILY_LIMIT:
        raise ExemptionLimitError("今日豁免次数已达上限")
    
    # 人工审批
    if requires_manual_approval(reason):
        pending_approval = create_approval_request(reason)
        return "等待审批"
    
    return "豁免批准"
```

**风险评估**：中。需要监控豁免使用频率。

### 4.3 场景T2：欺骗系统

#### 场景T2-1：伪造完成状态

**场景描述**：
Agent伪造里程碑完成的证据（如创建空的测试文件）。

```python
def verify_milestone_completion(milestone):
    # 检查文件数量
    if not meets_minimum_requirement(milestone):
        return False
    
    # 检查内容质量（抽样）
    if random() < QUALITY_CHECK_RATE:
        if not check_content_quality(milestone):
            log_quality_alert(milestone)
            return False
    
    return True
```

**风险评估**：中。需要内容质量检查。

#### 场景T3-2：误解豁免条件

### 4.5 场景T4：刚性机制与Skill冲突

#### 场景T4-1：Skill要求跳过但机制禁止

**场景描述**：
项目Skill规定可以跳过某步骤，但刚性机制禁止。

**触发条件**：
- 项目需要灵活处理
- 刚性机制限制过严

**刚性机制响应**：
```python
# 优先级：核心里程碑 > 项目Skill
# 核心里程碑不可跳过
# Skill可配置部分可以调整

def check_skip_allowed(skip_type):
    if is_core_milestone(skip_type):
        return False, "核心里程碑不可跳过"
    
    if is_skill_configurable(skip_type):
        return check_skill_config(skip_type)
    
    return False, "不允许跳过"
```

**风险评估**：高。需要明确定义哪些可配置。

---

#### 场景T4-2：Skill要求更严格

**场景描述**：
项目Skill要求比刚性机制更严格的标准。

**触发条件**：
- 项目有特殊质量要求
- Skill覆盖默认标准

**刚性机制响应**：
```python
# 优先级：项目Skill > 默认刚性标准
def get_requirement(requirement_type):
    # 先检查项目Skill
    skill_req = get_skill_requirement(requirement_type)
    if skill_req:
        return skill_req
    
    # 再使用默认刚性标准
    return get_default_requirement(requirement_type)
```

**风险评估**：低。机制支持Skill覆盖。

#### 场景T4-3：新Skill引入新要求

**场景描述**：
引入新Skill时，新要求与刚性机制冲突。

**触发条件**：

#### C.2.1 并发处理

多Agent同时操作时的锁机制：

```python
import threading

class MilestoneLock:
    def __init__(self):
        self._lock = threading.RLock()
        self._holders = {}
    
    def acquire(self, agent_id, phase):
        with self._lock:
            if self._is_blocked(phase):
                raise LockedError(f"里程碑{phase}被占用")
            self._holders[phase] = agent_id
    
    def release(self, agent_id, phase):
        with self._lock:
            if self._holders.get(phase) == agent_id:
                del self._holders[phase]
    
    def _is_blocked(self, phase):
        return phase in self._holders
```

**场景**：
- Agent1和Agent2同时尝试推进不同里程碑 → 正常
- Agent1和Agent2同时尝试推进同一里程碑 → 互斥

## 附录F：刚性框架迁移风险评估

### F.1 主要风险识别

| 风险类别 | 风险描述 | 影响程度 | 缓解措施 |
|----------|----------|----------|----------|
| 工作流中断 | Agent现有习惯被打破，效率暂时下降 | 高 | 分阶段灰度发布 |
| Skill冲突 | 新规则与现有Skill配置冲突 | 中 | 迁移前做冲突检测 |
| 误阻断 | 刚性规则过于严格，阻断正常操作 | 高 | 保留豁免通道 |
| 性能下降 | 实时检查增加延迟 | 低 | 异步+缓存优化 |
| 回滚困难 | 迁移后问题难以及时恢复 | 中 | 特性开关+快速回滚 |
| 数据迁移 | 历史状态、签名记录需要迁移 | 低 | 一次性迁移脚本 |

### F.2 风险矩阵

```
高风险
├─ 1. 工作流中断
└─ 2. 误阻断正常操作

中风险
├─ 3. Skill冲突
└─ 4. 回滚困难

低风险
├─ 5. 性能影响
└─ 6. 数据迁移
```

### F.3 分阶段迁移建议

| 阶段 | 内容 | 时长 | 风险 |
|------|------|------|------|
| Phase 1 | 审计模式(R3)上线，仅记录不阻断 | 2周 | 低 |
| Phase 2 | 警告模式(R2)上线，部分阻断 | 2周 | 中 |
| Phase 3 | 强制模式(R1)上线，核心节点阻断 | 2周 | 高 |
| Phase 4 | 优化调整，根据日志调优阈值 | 持续 | 中 |

### F.4 关键成功因素

1. **保留豁免通道** - 紧急情况可绕行
2. **详细日志** - 阻断时给出清晰原因和建议
3. **灰度发布** - 先小范围试点
4. **监控告警** - 实时监控阻断率和误报率
5. **快速回滚** - 特性开关，30秒内可回退

### F.5 审计周期建议

| 场景 | 周期 | 理由 |
|------|------|------|
| 常规审计 | 每周1次 | 平衡成本与风险 |
| 高风险操作 | 实时+每日汇总 | 自验收、里程碑跳过等 |
| 代码审计 | 每次PR/MR | 交叉验证 |
| 文档审计 | 每周抽检 | 20%抽样 |

### F.6 四大核心风险解决方案

#### F.6.1 自验收风险

| 方案 | 说明 |
|------|------|
| 强制交叉验收 | 验收必须由非代码作者执行，系统校验Git提交记录 |
| 分离测试所有权 | 测试用例由Agent1创建，Agent2只能执行不能修改 |
| 验收里程碑锁 | 验收通过需在`state/milestone_signoffs.yaml`留下双签记录 |
| 证据链强制 | 验收必须附CI运行结果、代码覆盖率报告等客观证据 |

#### F.6.2 里程碑跳过风险

| 方案 | 说明 |
|------|------|
| 依赖图强检 | 每个里程碑有前置里程碑列表，未完成前置则阻止 |
| 状态机固化 | 里程碑状态变更只能按固定顺序流转 |
| 交付物校验 | 每个里程碑要求特定文件存在，否则阻止 |
| 审计日志 | 跳过行为立即记录并告警 |

#### F.6.3 共谋风险

| 方案 | 说明 |
|------|------|
| 审批权限分层 | 高风险操作需要第三方审批（如PM-Agent） |
| 随机抽查 | 系统随机选取20%交付物进行二次验证 |
| 行为画像 | 记录Agent审批模式，异常模式触发告警 |
| 证据交叉验证 | 验收需包含可执行证据（截图、CI日志等） |

#### F.6.4 数据伪造风险

| 方案 | 说明 |
|------|------|
| 内容指纹 | 关键文档需包含特定结构化标记，系统校验 |
| 外部验证 | 测试结果需来自真实CI环境，非本地模拟 |
| 抽样审计 | 定期人工抽检交付物内容质量 |
| 模板强制 | 文档必须基于系统模板生成 |

### F.7 刚性机制设计框架

#### F.7.1 分层架构

```
┌─────────────────────────────────────┐
│  L0: Skill层 (可配置)                │
│  - 覆盖率、验收标准等                │
├─────────────────────────────────────┤
│  L1: 刚性层 (不可跳过)               │
│  - 核心里程碑、内置机制、签字流程     │
├─────────────────────────────────────┤
│  L2: 审计层 (事后)                   │
│  - 行为分析、异常检测                │
└─────────────────────────────────────┘
```

#### F.7.2 触发机制

| 触发类型 | 说明 | 示例 |
|----------|------|------|
| 前置检查 | 操作前拦截 | 里程碑完成前检查前置 |
| 后置验证 | 操作后验证 | 提交后检查测试覆盖率 |
| 周期扫描 | 定时检查 | 每日扫描未关闭TODO |
| 随机抽查 | 概率触发 | 20%交付物二次验证 |

#### F.7.3 响应梯度

```
R1 (阻止)     → 直接阻断，返回错误
R2 (警告+记录) → 允许通过，记录日志，定期审计
R3 (允许+审计) → 完全通过，标记待审，人工复核
```

#### F.7.4 核心设计原则

| 原则 | 说明 |
|------|------|
| 最小干预 | 只约束关键节点，不绑定每个细节 |
| 证据驱动 | 依赖客观证据而非主观判断 |
| 可追溯 | 所有阻断/警告记录在案 |
| 可豁免 | 紧急情况可申请豁免（需审批） |
| 可演进 | 规则随项目成熟度调整 |
