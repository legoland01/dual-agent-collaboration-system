## 第一部分：F-GIT-001 重复造轮子问题

### 1.1 事实核查

**需求声称**:
> "Git 同步强制机制是新增功能"

**实际情况**:

```python
# src/core/auto_git_sync.py - 已存在！
class AutoGitSyncEngine:
    def detect_changes(self) -> List[str]: ...
    def auto_add(self) -> Dict[str, Any]: ...
    def auto_commit(self, message: str = "自动提交") -> Dict[str, Any]: ...
    def auto_push(self) -> Dict[str, Any]: ...
    def sync_all(self) -> Dict[str, Any]: ...
```

**问题**:

| 需求说的 | 实际已实现的 | 差异 |
|----------|--------------|------|
| "新增 git sync 命令" | `sync_all()` 已存在 | 命令名不同 |
| "修改 phase-advance" | 无集成 | 需要集成 |
| "未同步警告" | 无 | 需新增 |
| 预估 9h | 已实现 70%+ | 严重高估 |

### 1.2 核心质疑

**质疑 1**: 为什么需求文档说 F-GIT-001 是"新增功能"，但 auto_git_sync.py 已经在 v2.2.1 中实现？

**质疑 2**: 9h 的工时预估是怎么算出来的？
```
需求文档: 9h
├── 修改 phase-advance: 2h
├── 修改 todo done: 1h  
├── 新增 git sync 命令: 3h
├── 未同步警告机制: 2h
└── 错误处理: 1h

实际分析:
├── auto_git_sync.py 已存在 → 减去 70%
├── phase_advance.py 已存在 → 减去 2h
├── 未同步警告 → 新增，但简单
└── 实际工作量: 约 3h
```

**质疑 3**: F-GIT-001 的真正问题是什么？

| 场景 | 当前行为 | 问题本质 |
|------|----------|----------|
| auto_git_sync.py 存在 | 未被调用 | **集成问题**，不是功能缺失 |
| phase_advance.py 存在 | 未调用 sync | **集成问题**，不是功能缺失 |
| 用户忘记 sync | 无警告 | **行为问题**，不是功能缺失 |

### 1.3 结论

**F-GIT-001 应该改为**:

```
F-GIT-001: Git 同步集成机制（不是"强制"）

核心问题: auto_git_sync.py 已存在，但未被使用
解决方案: 集成到现有流程，而非重写

验收标准:
- [ ] phase_advance.py 自动调用 auto_git_sync
- [ ] 添加未同步警告
- [ ] 提供手动 sync 命令（封装已有功能）

工时预估: 3h（集成 + 警告 + CLI 封装）
```

## 第三部分：F-PROC-003 编号迁移风险

### 3.1 迁移复杂度分析

**现状**:
```
state/agent_adhoc_todos.yaml 中有:
- TODO-001 到 TODO-032
- 所有文档引用 TODO-xxx 格式
```

**F-PROC-003 变更**:
```
格式: TODO-xxx → {AgentID}-xxx

例如:
- TODO-001 → 1-001 (Agent1 创建)
- TODO-002 → 2-002 (Agent2 创建)
```

### 3.2 核心质疑

**质疑 1**: 迁移脚本真的能完美工作吗？

```python
# 迁移伪代码
def migrate():
    todos = load_todos()
    for todo in todos:
        # 根据创建者判断
        if todo.from == "agent1":
            todo.id = f"1-{next序号()}"
        elif todo.from == "agent2":
            todo.id = f"2-{next序号()}"
    save_todos()
```

**问题**:
- `from` 字段准确吗？
- `to` 字段怎么办？
- 并发迁移怎么办？
- 迁移失败怎么回滚？

**质疑 2**: 文档引用怎么办？

```
所有引用 TODO-xxx 的文档:
├── PROPOSAL_*.md
├── REVIEW_*.md
├── requirements_*.md
└── state/*.yaml

数量: 20+ 文档
```

**方案**:
- 逐个手动更新？不现实
- 自动替换？可能出错
- 渐进式迁移？过渡期混乱

**质疑 3**: 双格式兼容期有多长？

```
理想: 1 周
实际: 1-2 个月
```

**期间**:
- Agent1 用新格式
- Agent2 用新格式
- 人工协作？用哪种格式？
- 混乱: "你说的 TODO-001 是哪个？"

### 3.3 结论

**F-PROC-003 需要**:

1. **详细迁移方案**: 不能只是一个"迁移脚本自动更新"
2. **回滚机制**: 迁移失败怎么办
3. **文档更新计划**: 20+ 文档怎么更新
4. **过渡期策略**: 双格式期间怎么协作

**建议**: 推迟到 v2.3.0 实现，v2.2.2 聚焦核心功能
