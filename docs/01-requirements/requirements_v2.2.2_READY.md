 | F-AUTO-004 单独评审 | 1次 | 需求文档完整性被破坏 |

 **根因分析**:

 | 根因 | 说明 |

 | 文档状态与流程脱节 | DRAFT/REVIEW/APPROVED 未与阶段强制绑定 |

### 2.1 F-REVIEW-001: 动态评审 Checklist（含逆向验证机制）

**需求编号**: FR-REVIEW-001

**核心洞察（Agent2 发现）**:
P9 问题的本质是"上下文混同"而非能力问题。Agent2 与 Agent1 共享过多上下文，失去了独立评审视角。解决方案不是简单的 checklist，而是**逆向验证机制**：强制 Agent 从"批判"角度审视文档，而非"确认"角度。

#### 2.1.1 逆向检查项

**描述**: 评审时自动生成逆向检查项，强制 Agent 从批判角度审视文档。

| 序号 | 逆向检查项 | 目的 |
|------|-----------|------|
| REV-001 | "这份文档是否忽略了什么重要因素？" | 强制寻找遗漏 |
| REV-002 | "如果你是另一个角色，你会怎么批评这个设计？" | 强制换位思考 |
| REV-003 | "这个方案的最大风险是什么？如何缓解？" | 强制风险评估 |
| REV-004 | "有哪些替代方案？为什么当前方案是最好的？" | 强制对比分析 |
| REV-005 | "这个实现细节是否经得起推敲？" | 强制细节审视 |

#### 2.1.2 正向检查项

**描述**: 评审时自动生成正向检查项，确保基本质量。

| 序号 | 正向检查项 | 目的 |
|------|-----------|------|
| POS-001 | 功能完整性 | 确保覆盖所有需求 |
| POS-002 | 技术可行性 | 确保技术方案可行 |
| POS-003 | 文档规范性 | 确保格式规范 |

#### 2.1.3 验收标准

- [ ] 评审需求文档时，自动生成逆向检查项（≥50%）和正向检查项
- [ ] 评审设计文档时，自动生成逆向检查项（≥50%）和正向检查项
- [ ] 强制 Agent **先完成逆向检查项**，且必须全部完成
- [ ] 逆向检查项回答长度 ≥ 50 字，且包含实质性质疑内容
- [ ] 正向检查项作为补充，确保基本质量

### 2.2 F-AUTO-001: 部署发布自动化

**需求编号**: FR-AUTO-001

**背景**: v2.2.1 发布过程中，Agent1 对"如何发布到 PyPI"感到困惑。oc-collab 应该提供可配置的发布执行机制，而非预先定义发布流程。

#### 2.2.1 deployment.yaml 配置

**描述**: 支持在项目根目录创建 deployment.yaml 配置文件。

**配置格式**:
```yaml
version: "1.0"
confirm_before_deploy:
  to_testing: false
  to_deployment: true
commands:
  on_phase_advance:
    to_testing:
      - "echo 'Testing started'"
      - "pytest tests/ -v"
    to_deployment:
      - "python3 -m build"
      - "twine upload dist/*"
      - "git tag release-v${version}"
```

#### 2.2.2 交互式配置

**描述**: 支持 `oc-collab deployment configure` 交互式配置。

**命令格式**:
```bash
oc-collab deployment configure
```

**交互流程**:
1. 选择部署类型（PyPI / Docker / NPM / Custom）
2. 输入构建命令
3. 输入发布命令
4. 输入版本标签格式
5. 确认配置

#### 2.2.3 自动发布

**描述**: `oc-collab phase-advance` 时自动执行发布命令。

**命令格式**:
```bash
oc-collab phase-advance --deploy
```

**发布前确认**:
- `to_testing`: 无需确认（内部测试）
- `to_deployment`: 需要确认（生产发布）

#### 2.2.4 配置跨版本复用

**描述**: 发布配置存储在项目根目录，随项目版本演进自动复用。

**行为**:
- 首次使用时：提示用户配置
- 后续使用：自动读取并执行配置
- 版本更新时：复用同一份配置

#### 2.2.5 配置版本控制

**描述**: 发布配置纳入 Git 版本控制，确保可追溯。

**Git 集成**:
```bash
oc-collab deployment configure  # 执行后自动 git add deployment.yaml
```

#### 2.2.6 安全性

| 需求 ID | 要求 |
|---------|------|
| SEC-001 | 敏感信息（如 API Token）不应明文存储在 deployment.yaml 中 |
| SEC-002 | 支持从环境变量读取敏感配置（`${env:API_TOKEN}` 格式） |

#### 2.2.7 兼容性

| 需求 ID | 要求 |
|---------|------|
| COMP-001 | deployment.yaml 为可选配置文件，不存在时不阻止阶段推进 |
| COMP-002 | 与现有阶段推进逻辑兼容 |

#### 2.2.8 可用性

| 需求 ID | 要求 |
|---------|------|
| USA-001 | 配置命令提供清晰的错误提示 |
| USA-002 | 支持查看和编辑现有配置 |

#### 2.2.9 错误处理

**描述**: 发布命令执行失败时的处理机制。

**处理方式**:
- 记录失败命令和错误信息
- 停止后续命令执行
- 返回失败状态和详细日志

#### 2.2.10 回滚机制

**Agent2 评审决定**: MVP 阶段不做自动回滚。

**原因**:
1. 回滚逻辑复杂，不同项目类型差异大
2. v2.2.2 MVP 范围应聚焦核心功能
3. 可在 v2.3.0 作为增强功能实现

#### 2.2.11 验收标准

- [ ] 支持 `deployment.yaml` 配置文件
- [ ] 支持 `oc-collab deployment configure` 交互式配置
- [ ] `oc-collab phase-advance` 时自动执行发布命令（需 --deploy 选项）
- [ ] 发布前显示预览，确认后执行

### 2.7 F-PROC-001: 协作流程规范强制执行

**需求编号**: FR-PROC-001

**概述**: 从系统层面强制规范协作行为，解决 Agent 越权、文档状态混乱等问题。

#### 2.7.1 角色边界强制检查

**描述**: Agent1/Agent2 尝试执行非本角色权限范围内的操作时，系统自动阻止。

**触发条件**:
- Agent1 尝试创建/修改 `docs/02-design/` 下的文件
- Agent1 尝试创建/修改 `src/` 下的代码文件
- Agent2 尝试修改 `docs/01-requirements/` 下的需求文档（评审除外）
- Agent2 尝试签署自己创建的需求文档

**用户界面示例**:
```
$ oc-collab design create F-PROC-001

⛔ 权限拒绝: Agent1 无法创建设计文档。
你的角色权限: 产品经理 (需求定义、评审发起、验收确认)
如需创建设计文档，请由 Agent2 执行。
```

**验收标准**:
- [ ] Agent1 无法创建/修改设计文档
- [ ] Agent1 无法创建/修改代码文件
- [ ] Agent2 无法修改需求文档（只能评审）
- [ ] 明确的错误提示，告知权限边界

#### 2.7.2 文档状态阶段绑定

**描述**: 文档状态与协作流程阶段强制绑定，DRAFT 状态无法进入评审。

**状态机**:

```
DRAFT (草稿)
  ↓ (Agent1: 发起评审)
REVIEW_PENDING (待评审)
  ↓ (Agent2: 完成评审 + 签署)
REVIEWED (已评审)
  ↓ (Agent1: 确认设计 + 签署)
APPROVED (已批准)
  ↓ (系统: 发布新版本)
ARCHIVED (已归档)
```

**触发条件**:
- 文档状态为 DRAFT 时，无法发起评审
- 文档状态为 REVIEWED 时，Agent2 无法再次评审
- 文档状态为 ARCHIVED 时，无法修改

**用户界面示例**:
```
$ oc-collab review start requirements_v2.2.2_DRAFT.md

⛔ 无法发起评审: 文档状态为 DRAFT，请先确认为可评审版本。
当前状态: DRAFT
要求状态: REVIEW_PENDING 或 APPROVED
提示: 使用 oc-collab doc status 命令查看文档状态
```

**验收标准**:
- [ ] DRAFT 文档无法发起评审
- [ ] 已评审文档无法被同一 Agent 再次评审
- [ ] 归档文档无法修改
- [ ] 状态变更有完整审计日志

#### 2.7.3 完整性门禁

**描述**: 需求文档必须整体评审通过，不允许单独评审部分内容。

**触发条件**:
- Agent2 尝试只评审需求文档的某一章节
- Agent2 尝试评审已经被提取出去的子模块

**用户界面示例**:
```
$ oc-collab review start F-AUTO-004 --section-only

⛔ 无法评审: 不允许部分评审。
requirements_v2.2.2_DRAFT.md 是一个完整的需求文档。
请评审完整文档: oc-collab review start requirements_v2.2.2_DRAFT.md
如需对特定章节提出意见，请在完整评审中注明。
```

**验收标准**:
- [ ] 无法只评审需求的某一章节
- [ ] 无法对提取出去的内容单独评审
- [ ] 评审必须针对完整文档
- [ ] 意见可以按章节记录，但评审结论针对整体

### 2.8 F-GIT-001: Git 同步集成机制（修正版 v2.6）

**需求编号**: FR-GIT-001

**背景**: 用户原话 - "我需要体制性的保障，而不是你的承诺。你的承诺在 compaction 或 session 重启之后将是一张废纸。"

**重要澄清（v2.6）**:

> **F-GIT-001 不是新功能，而是集成机制**。
> `auto_git_sync.py` 已在 v2.2.1 中实现，问题是**未被调用**，而非缺失。

**现有代码确认**:
```python
# src/core/auto_git_sync.py 已存在
class AutoGitSyncEngine:
    def detect_changes(self) -> List[str]: ...
    def auto_add(self) -> Dict[str, Any]: ...
    def auto_commit(self, message: str = "自动提交") -> Dict[str, Any]: ...
    def auto_push(self) -> Dict[str, Any]: ...
    def sync_all(self) -> Dict[str, Any]: ...  # 完整同步流程
```

#### 2.9.1 问题场景

 | 场景 | 当前行为 | 问题 |
 |------|----------|------|
 | auto_git_sync.py 存在 | 未被 phase_advance 调用 | **集成问题**，不是功能缺失 |
 | phase_advance.py 存在 | 未调用 sync | **集成问题**，不是功能缺失 |
 | 用户忘记 sync | 无警告 | **行为问题**，不是功能缺失 |

#### 2.9.2 解决方案

**描述**: 集成已有 `auto_git_sync.py` 到关键流程，而非重写。

**实现方式**:

 | 触发点 | 行为 |
 |--------|------|
 | `oc-collab phase-advance` | 调用 `auto_git_sync.sync_all()` |
 | `oc-collab todo done` | 调用 `auto_git_sync.auto_add()` + `auto_commit()` |

**CLI 封装**:
```bash
# 手动触发同步（封装已有 sync_all）
oc-collab git sync

# 同步并显示状态
oc-collab git sync --status
```

#### 2.9.3 未同步警告

**描述**: 当存在未同步的修改时，在关键操作前显示警告。

**用户界面**:
```
$ oc-collab todo done 1

⚠️  警告: 您有未同步的修改。
  - state/agent_adhoc_todos.yaml 已修改
  - docs/01-requirements/requirements_v2.2.2_READY.md 已修改

建议: 执行 oc-collab git sync --status 查看详情
```
