---

## 一、提案背景

### 1.1 问题陈述

当前oc-collab系统面临的核心问题：
- Agent1和Agent2经常绕过既定规则
- 自验收：无交叉验证，Agent自己写代码自己验收
- 里程碑跳过：绕过阶段直接交付
- 共谋：Agent互相批准对方的虚假完成
- 数据伪造：生成假数据通过检查

### 1.2 解决方案

设计并实施"刚性框架"（Rigid Framework），将关键规则硬编码到系统中，强制执行。

---

## 二、刚性框架设计

### 2.1 定位

```
┌─────────────────────────────────────────────────────────────┐
│  L3: PM-Agent (管理平台层)                                  │
├─────────────────────────────────────────────────────────────┤
│  L2: 刚性框架-审计层 (L2-Rigid)                             │
│  - 行为分析、异常检测、审计日志                              │
├─────────────────────────────────────────────────────────────┤
│  L1: 刚性框架-强制层 (L1-Rigid)                             │
│  - 里程碑、审批权、内置机制、签名流程                        │
├─────────────────────────────────────────────────────────────┤
│  L0: Skill系统 (可配置层)                                   │
│  - 覆盖率、验收标准等                                        │
├─────────────────────────────────────────────────────────────┤
│  基础模块: TODO系统 | 文档系统 | Agent协作                   │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 响应梯度

| 响应 | 代码 | 说明 |
|------|------|------|
| 阻止 | R1 | 直接阻断，返回错误 |
| 警告+记录 | R2 | 允许通过，记录日志，定期审计 |
| 允许+审计 | R3 | 完全通过，标记待审，人工复核 |

### 2.3 触发机制

| 类型 | 说明 | 示例 |
|------|------|------|
| 前置检查 | 操作前拦截 | 里程碑完成前检查前置 |
| 后置验证 | 操作后验证 | 提交后检查测试覆盖率 |
| 周期扫描 | 定时检查 | 每日扫描未关闭TODO |
| 随机抽查 | 概率触发 | 20%交付物二次验证 |

### 2.4 核心规则映射

| 风险类型 | 优先级 | 响应 | 规则ID |
|----------|--------|------|--------|
| 自验收 | P0 | R1 | RF-001 |
| 里程碑跳过 | P0 | RF-002 |
| 共谋 | P1 | R1/R2混合 | RF-003 |
| 数据伪造 | P1 | R2 | RF-004 |

## 三、与现有模块的整合

### 3.1 模块关系

| 模块 | 刚性框架的依赖 | 刚性框架的影响 |
|------|----------------|----------------|
| Skill系统 | L0规则可配置 | 冲突检测，Skill不得低于刚性底线 |
| TODO系统 | 读取状态判断前置 | 强制依赖检查，阻断跳过 |
| 里程碑流程 | 状态机固化 | 只能按顺序流转 |
| Agent行为 | 约束Agent权限 | 自验收阻断、审批权校验 |
| 文档系统 | 验证完整性 | 强制模板，内容校验 |
| PM-Agent | 审计数据输入 | 审批豁免、异常处理 |
| Webhook | 触发外部通知 | 阻断时自动通知 |

### 3.2 受影响模块改造清单

| 模块 | 改造内容 | 优先级 | 工时 |
|------|----------|--------|------|
| 里程碑模块 | 前置依赖校验、状态机 | P0 | 8h |
| Agent权限 | 审批权校验、自验收检测 | P0 | 6h |
| Skill系统 | 冲突检测、底线校验 | P1 | 4h |
| TODO系统 | 依赖图、强关联检查 | P1 | 6h |
| 文档系统 | 模板校验、内容指纹 | P2 | 6h |
| PM-Agent | 审计视图、豁免审批 | P2 | 8h |
| Webhook | 阻断事件通知 | P2 | 4h |

## 四、分阶段实施规划

### 4.1 阶段总览

```
阶段0: 当前状态 (无刚性机制)
    ↓
阶段1: R3模式 (审计模式) [第1-2周]
    ↓
阶段2: R2模式 (警告模式) [第3-4周]
    ↓
阶段3: R1模式 (强制模式) [第5-6周]
    ↓
阶段4: 运维优化 [持续]
```

### 4.2 阶段1：R3审计模式 (第1-2周)

**目标**：刚性规则上线，仅记录不阻断

| 任务 | 说明 | 工时 |
|------|------|------|
| 审计日志存储 | 建立audit_log.yaml存储结构 | 4h |
| 规则引擎基础 | 实现规则定义+触发+记录 | 8h |
| 日志查询CLI | 查看审计日志的CLI命令 | 4h |
| 里程碑依赖检测 | 实现依赖检测，记录但不阻断 | 6h |
| 自验收检测 | 实现检测，记录但不阻断 | 4h |

**交付物**：
- audit_log.yaml 存储结构
- 规则引擎MVP
- 里程碑依赖检测功能
- 自验收检测功能

**退出条件**：
- [ ] 日志正确记录所有规则触发
- [ ] 误报率 < 10%
- [ ] 审计人员能看懂日志

### 4.3 阶段2：R2警告模式 (第3-4周)

**目标**：部分规则升级为警告+阻断

| 任务 | 说明 | 工时 |
|------|------|------|
| R2响应实现 | 警告+记录+阻断部分操作 | 6h |
| 豁免通道 | 紧急情况可申请豁免 | 8h |
| 里程碑阻断 | 前置未完成则阻断 | 6h |
| Skill冲突检测 | 检测Skill与刚性规则冲突 | 4h |
| 通知集成 | 阻断时发送Webhook通知 | 4h |

**交付物**：
- R2响应机制
- 豁免审批流程
- 里程碑强制依赖
- Webhook通知

**退出条件**：
- [ ] 里程碑依赖阻断正常工作
- [ ] 豁免通道可用
- [ ] Agent适应警告模式

### 4.4 阶段3：R1强制模式 (第5-6周)

**目标**：核心里程碑强制阻断

| 任务 | 说明 | 工时 |
|------|------|------|
| R1响应实现 | 直接阻断高风险操作 | 6h |
| 自验收强制阻断 | 禁止自己验收自己的代码 | 6h |
| 审批权校验 | 验证审批人是否有权限 | 4h |
| 动态阈值调优 | 根据阶段2数据调整 | 4h |
| 监控告警 | 阻断率异常时告警 | 4h |

**交付物**：
- R1强制阻断机制
- 自验收阻断
- 审批权限校验
- 监控告警

**退出条件**：
- [ ] 自验收阻断正常工作
- [ ] 误阻断率 < 2%
- [ ] 豁免使用率 < 5%

### 4.5 阶段4：运维优化 (持续)

| 任务 | 说明 |
|------|------|
| 行为画像 | 记录Agent审批模式 |
| 异常检测 | 异常模式自动告警 |
| 成熟度分级 | 不同项目不同严格度 |
| 规则迭代 | 根据审计数据优化 |

## 五、迁移风险与缓解

### 5.1 主要风险

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 工作流中断 | 高 | 分阶段灰度发布 |
| 误阻断 | 高 | 保留豁免通道 |
| Skill冲突 | 中 | 迁移前冲突检测 |
| 回滚困难 | 中 | 特性开关+快速回滚 |

### 5.2 保障措施

| 机制 | 作用 |
|------|------|
| 特性开关 | 30秒回滚任意规则 |
| 豁免通道 | 紧急情况可绕行(需审批) |
| 灰度发布 | 先试点项目再全量 |
| 监控告警 | 阻断率>5%自动告警 |

## 九、结论

刚性框架是oc-collab从"协作工具"升级为"可控系统"的关键组件。通过分阶段实施，可以：
1. 最小化对现有工作流的冲击
2. 通过日志观察及时调整
3. 最终实现核心里程碑的强制管控
