## Part 1: 版本规划新标准

### 一、背景

#### 1.1 问题陈述

当前版本规划采用"按工时切分"的方式：将评估的工时作为版本大小的唯一衡量标准，目标是每个版本控制在固定工时内（如40h）。

**问题**：
- 工时评估过于保守，实际开发时间往往远小于评估时间
- 保守的工时估计导致每个版本承载的feature过少
- 开发时间短，流程成本（评审、签署、部署）相对固定
- 频繁的小版本导致流程占比过高，严重拖累进度

#### 1.2 核心矛盾

| 因素 | 影响 |
|------|------|
| 保守的工时评估 | 版本feature过少 |
| 流程成本固定 | 小版本流程占比高 |
| 开发周期短 | 低估的工时可以容纳更多feature |

---

### 二、核心观点

#### 2.1 版本大小的衡量方式应该改变

| 当前方式 | 建议方式 |
|----------|----------|
| 按工时切分 | 按功能包分组 |
| 目标：控制工时在固定范围 | 目标：最大化开发效率 |
| 保守估计 | 风险分级 |

#### 2.2 功能包原则

**定义**：一个功能包（Feature Package）是一组相互关联、功能上相对独立的需求，它们：

- 一起开发和一起测试效率更高
- 有共同的目标或用户价值
- 可以独立部署和验证

**分组依据**：
| 原则 | 说明 |
|------|------|
| 功能相关性 | 同一个模块/功能的feature打包 |
| 依赖关系 | 有依赖的feature一起规划 |
| 测试便利性 | 可以一起测试的feature打包 |
| 风险等级 | 同等风险等级的feature打包 |

#### 2.3 风险分级

| 风险等级 | 特征 | 建议 |
|----------|------|------|
| **P0** | 核心功能，影响现有逻辑，可能引入回归 | 单独版本，小范围测试 |
| **P1** | 重要功能，但不改变核心逻辑 | 可与低风险feature打包 |
| **P2** | 优化、改进、非关键功能 | 可积攒多个一起发布 |

---

### 三、新版本规划流程

#### 3.1 流程对比

| 步骤 | 当前流程 | 建议流程 |
|------|----------|----------|
| 1 | 收集所有待实现feature | 收集所有待实现feature |
| 2 | 评估每个feature的工时 | 按功能相关性分组 |
| 3 | 按固定工时切分版本 | 按风险等级标记每个功能包 |
| 4 | 分配到各版本 | 确定每个功能包的优先级 |
| 5 | 评审通过后开发 | 评审通过后开发 |

#### 3.2 决策矩阵

```
功能包大小评估矩阵：

                    功能包内feature数量
                    少          多
风险等级  低  ──────────────────────
高        ──────────────────────

建议：
- 低风险 + 多feature：优先纳入当前版本
- 低风险 + 少feature：可积攒
- 高风险 + 多feature：拆分或延后
- 高风险 + 少feature：单独版本，重点测试
```

---

### 四、实施建议

#### 4.1 短期（v2.2.x）

- 在版本规划时，先按功能相关性分组
- 不再以"40h"作为硬性限制
- 记录实际工时，用于校准评估模型

#### 4.2 中期（v3.0）

- 建立功能包模板
- 开发风险评估工具
- 积累实际数据，优化分组策略

#### 4.3 评估校准

| 阶段 | 行动 |
|------|------|
| 规划时 | 记录评估工时 |
| 开发时 | 记录实际工时 |
| 完成后 | 对比评估vs实际，校准系数 |

---

### 五、预期收益

| 收益 | 说明 |
|------|------|
| 减少版本数量 | 相同的开发量，更少的版本切换 |
| 降低流程成本 | 减少评审、签署、部署的次数 |
| 提高开发效率 | 减少等待和切换开销 |
| 更合理的评估 | 基于实际数据持续校准 |

---

### 六、风险与应对

| 风险 | 应对措施 |
|------|----------|
| 功能包划分不合理 | 先试行，按效果调整 |
| 测试覆盖不足 | 引入自动化测试，强化回归测试 |
| 版本过大难以管理 | 区分核心包和附加包，核心包保持小规模 |

## Part 2: L1 Skill系统设计

### 一、背景：Skill的本质

| 属性 | 说明 |
|------|------|
| **SOP** | Skill定义项目如何运行 |
| **项目级** | 每个项目有自己的SOP |
| **可切换** | 不同项目/客户可以有不同的SOP |

---

### 二、分层架构中的Skill

```
┌─────────────────────────────────────────────────┐
│  L3: 管理平台层                                  │
│       ├── Skill模板市场/下发                      │
│       ├── 模板版本管理                           │
│       └── 项目Skill配置（锁定/解锁）              │
├─────────────────────────────────────────────────┤
│  L2: 接口/编排层                                 │
├─────────────────────────────────────────────────┤
│  L1: oc-collab-core                             │
│       ├── Skill运行时（加载、执行、强制）         │
│       ├── 缺省加载机制                           │
│       └── 自动升级机制                           │
└─────────────────────────────────────────────────┘
```

---

### 三、核心能力设计

#### 3.1 模板机制

| 能力 | 说明 |
|------|------|
| **标准模板** | 默认使用标准Skill模板 |
| **模板继承** | 基于标准模板创建项目变体 |
| **模板下发** | 从主项目同步到子项目 |

#### 3.2 生命周期

```
创建项目 → 缺省加载标准模板 → 使用/修改 → 锁定(可选) → 自动升级(可选)
```

#### 3.3 缺省加载

| 场景 | 行为 |
|------|------|
| 新项目创建 | 自动加载标准Skill模板 |
| 中途接入项目 | 提示选择模板或从主项目同步 |

#### 3.4 锁定机制

| 场景 | 行为 |
|------|------|
| 锁定状态 | 强制使用标准模板，不允许修改 |
| 解锁状态 | 可根据项目情况定制 |
| 权限 | 只有项目owner可以锁定/解锁 |

**示意**：
```
项目A: 使用标准模板 → 不可修改（owner锁定）
项目B: 使用标准模板 → 可修改
项目C: 自定义模板 → 基于标准修改
```

#### 3.5 自动升级

| 机制 | 说明 |
|------|------|
| **版本检测** | 检测主项目Skill版本与项目当前版本 |
| **变更记录** | 记录每次Skill变更内容 |
| **升级策略** | 可配置：自动升级 / 手动确认 / 关闭 |

---

### 四、L1 Skill系统功能需求

#### 4.1 模板管理

| 功能 | 说明 |
|------|------|
| TPL-001 | 创建项目时自动加载标准Skill模板 |
| TPL-002 | 基于标准模板创建项目变体 |
| TPL-003 | 模板版本管理（版本号、变更记录） |

#### 4.2 锁定控制

| 功能 | 说明 |
|------|------|
| LCK-001 | 项目owner可以锁定项目Skill（强制使用标准版） |
| LCK-002 | 锁定状态下禁止修改Skill |
| LCK-003 | 只有owner可以解锁 |

#### 4.3 自动升级

| 功能 | 说明 |
|------|------|
| UPG-001 | 检测主项目Skill版本变更 |
| UPG-002 | 自动同步最新Skill到项目 |
| UPG-003 | 支持手动确认升级（可关闭自动升级） |
| UPG-004 | 升级前备份当前Skill |

---

### 五、实施计划

#### 5.1 短期（v2.2.x - v2.3.x）

- 实现模板加载器
- 实现缺省加载机制
- 实现版本检测

#### 5.2 中期（v3.0）

- 实现锁定/解锁机制
- 实现自动升级
- 与L3管理平台对接

---

### 六、预期收益

| 收益 | 说明 |
|------|------|
| 快速接入 | 新项目一键使用标准模板 |
| 灵活定制 | 支持基于标准模板修改 |
| 质量控制 | 锁定机制保证关键项目使用标准SOP |
| 自动维护 | 自动升级减少手动同步成本 |

## 总结

**Part 1** 解决版本规划效率问题：
- 从"按工时切分"转向"按功能包分组"
- 功能相关性优先于工时评估

**Part 2** 解决Skill生命周期问题：
- 模板机制：快速接入 + 灵活定制
- 锁定机制：质量控制
- 自动升级：持续维护
