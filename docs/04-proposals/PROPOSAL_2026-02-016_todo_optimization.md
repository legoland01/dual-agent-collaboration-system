## 二、编号优化：创建者→接收者

### 2.1 设计背景

**问题**：BUG-20260216-003揭示了当前编号的歧义：
- Agent凭直觉认为编号体现"分配给谁"
- 实际编号只体现"创建者"
- 这导致了理解上的混淆

**解决思路**：与其扭转AI的直觉，不如从系统设计上消除歧义。

### 2.2 新编号设计

**格式**：`TODO-XtoY-xxx`

| 部分 | 含义 |
|------|------|
| X | 创建者Agent ID |
| to | 分隔符 |
| Y | 接收者Agent ID |
| xxx | 序号 |

### 2.3 示例

| 编号 | 含义 |
|------|------|
| TODO-1to2-001 | Agent1创建，分配给Agent2 |
| TODO-2to1-001 | Agent2创建，分配给Agent1 |
| TODO-1to3-001 | Agent1创建，分配给Agent3（多Agent场景） |
| TODO-1to1-001 | Agent1创建，自己执行 |

### 2.4 优势

| 优势 | 说明 |
|------|------|
| **消除歧义** | 创建者和接收者都明确 |
| **支持多Agent** | 可分配给任意Agent |
| **符合直觉** | AI的理解在系统中得到体现 |
| **可追溯** | 任务流转清晰可见 |

### 2.5 向后兼容

| 场景 | 处理方式 |
|------|----------|
| 旧格式TODO-1-xxx | 保持不变，视为TODO-1to1-xxx |
| 新格式TODO-1to2-xxx | 新系统支持 |

## 三、优化方向

### 3.1 来源标签

**目的**：区分TODO从哪里来

**方案**：
```yaml
- id: TODO-1-022
  content: 修复BUG-20260215-014
  source: BUG        # 来源：BUG / REQUIREMENT / FEEDBACK / MANUAL
```

**来源类型**：
| 来源 | 说明 |
|------|------|
| REQUIREMENT | 来自需求文档 |
| BUG | 来自BUG报告 |
| FEEDBACK | 来自客户/用户反馈 |
| MANUAL | 手动创建 |

---

### 3.2 事件驱动自动创建

**目的**：减少手动创建TODO的工作量

**触发事件**：
| 触发事件 | 自动创建 |
|----------|----------|
| 需求文档签署通过 | → 生成开发任务TODO |
| 设计文档签署通过 | → 生成实现任务TODO |
| BUG创建 | → 生成修复任务TODO |
| 任务完成 | → 自动建议下一步任务 |

---

### 3.3 TODO模板化

**目的**：不同类型任务使用不同模板

**模板示例**：

```yaml
# 需求任务模板
type: REQUIREMENT
template:
  - id: TODO-{agent}-{seq}
    content: "实现{需求ID}: {需求描述}"
    source: REQUIREMENT
    priority: {priority}
    acceptance_criteria: "{从需求继承的验收标准}"

# BUG修复模板  
type: BUG_FIX
template:
  - id: TODO-{agent}-{seq}
    content: "修复{BUG-ID}: {标题}"
    source: BUG
    priority: {severity}
    root_cause: ""
    fix_plan: ""
    test_case: ""
```

---

### 3.4 智能建议

**功能**：
| 功能 | 说明 |
|------|------|
| 自动建议 | 创建TODO时系统建议下一步任务 |
| 依赖推断 | 根据当前任务自动推断依赖 |
| 继承上下文 | 从需求文档继承验收标准到TODO |
