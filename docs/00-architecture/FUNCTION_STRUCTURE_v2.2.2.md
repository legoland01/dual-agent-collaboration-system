## 1. 设计目标

### 1.1 问题陈述

当前 oc-collab 系统存在以下功能结构问题：

| 问题类型 | 问题描述 | 影响 |
|----------|----------|------|
| **职责重叠** | Agent1 越权触碰设计/代码 | 流程混乱，职责不清 |
| **流程脱节** | DRAFT 文档被评审 | 需求完整性无法保证 |
| **完整性缺失** | 部分评审取代整体评审 | 需求文档被肢解 |
| **工具缺陷** | todowrite 不同步 | 无法依赖 todo 管理任务 |

### 1.2 设计目标

1. **功能边界清晰** — 明确 Agent1/Agent2 的功能操作边界
2. **流程强制规范** — DRAFT 状态无法发起评审
3. **完整性强制检查** — 不允许部分评审
4. **工具可用性修复** — todowrite 必须同步到文件

## 2. 功能结构总览

### 2.1 功能域划分

oc-collab 系统划分为 5 个功能域：

| 功能域 | 核心功能 | 负责人 |
|--------|----------|--------|
| **流程控制域** | 阶段管理、状态转换、推进控制 | Agent1/Agent2 |

| **协作执行域** | 签署、评审、任务管理 | Agent1/Agent2 |
| **自动化域** | Git 同步、部署发布、覆盖率检查 | Agent2 |
| **治理监控域** | 角色验证、完整性检查、异常处理 | 系统强制 |

## 3. 功能域详细设计

### 3.1 流程控制域

**职责**: 管理项目阶段、状态转换、推进控制

| 功能 | 操作者 | 输入 | 输出 |
|------|--------|------|------|
| 阶段查询 | Agent1/Agent2 | 无 | 当前阶段 |
| 阶段推进 | Agent1 | phase-advance | 新阶段 |
| 状态转换 | Agent1/Agent2 | 当前状态 | 新状态 |

**规则**:
1. 阶段必须按 `requirements → design → development → testing → deployment` 顺序推进
2. 阶段推进必须满足前置条件（签署完成）
3. 阶段状态变更必须记录在 `project_state.yaml`

### 3.2 文档管理域

**职责**: 管理需求文档、设计文档、版本控制

| 功能 | 操作者 | 权限说明 |
|------|--------|----------|
| 创建需求 | Agent1 | ✅ 允许 |
| 修改需求 | Agent1 | ✅ 允许 |
| 创建设计 | Agent2 | ✅ 允许 |
| 修改设计 | Agent2 | ✅ 允许 |
| 评审需求 | Agent2 | ✅ 允许（只能评审，不能修改） |
| 评审设计 | Agent1 | ✅ 允许（只能评审，不能修改） |

**规则**:
1. 需求文档必须放在 `docs/01-requirements/`
2. 设计文档必须放在 `docs/02-design/`
3. 文档状态必须标注（DRAFT / REVIEW_PENDING / APPROVED / ARCHIVED）
4. DRAFT 状态无法发起评审（强制）

### 3.3 协作执行域

**职责**: 管理签署、评审、任务

| 功能 | 操作者 | 规则 |
|------|--------|------|
| 需求签署 | Agent1/Agent2 | 必须先完成评审 |
| 设计签署 | Agent1/Agent2 | 必须先完成评审 |
| 评审发起 | Agent1 | 需求文档状态必须为 REVIEW_PENDING |
| 评审意见 | Agent2 | 必须针对完整文档，不允许部分评审 |
| 任务管理 | Agent1/Agent2 | todowrite 必须同步到文件 |

### 3.4 自动化域

**职责**: 自动化 Git 同步、部署发布、覆盖率检查

| 功能 | 操作者 | 触发条件 |
|------|--------|----------|
| Git 自动同步 | 系统 | 签署完成后自动触发 |
| 部署发布 | Agent1/Agent2 | phase-advance --deploy |
| 覆盖率检查 | 系统 | 代码提交时强制检查 |

### 3.5 治理监控域 ⭐ (v2.2.2 新增)

**职责**: 强制规范协作行为，防止越权操作

| 功能 | 编号 | 说明 |
|------|------|------|
| 角色边界检查 | F-PROC-001.1 | 检查 Agent 是否越权操作 |
| 文档状态绑定 | F-PROC-001.2 | 检查文档状态是否允许操作 |
| 完整性门禁 | F-PROC-001.3 | 检查是否允许部分评审 |
| 任务同步修复 | F-PROC-001.4 | 修复 todowrite 不同步 bug |

## 4. 功能边界规则

### 4.1 Agent1 边界

| 操作 | 允许 | 拒绝 |
|------|------|------|
| 创建/修改需求文档 | ✅ | |
| 发起需求评审 | ✅ |签署需求 | |
|  ✅ | |
| 评审设计文档 | ✅ | |
| 创建/修改设计文档 | | ❌ |
| 创建/修改代码文件 | | ❌ |
| 签署自己创建的需求 | | ❌ |

### 4.2 Agent2 边界

| 操作 | 允许 | 拒绝 |
|------|------|------|
| 评审需求文档 | ✅ | |
| 签署需求 | ✅ | |
| 创建/修改设计文档 | ✅ | |
| 创建/修改代码文件 | ✅ | |
| 签署自己创建的设计 | | ❌ |
| 修改已签署的需求 | | ❌ |
| 修改已签署的设计 | | ❌ |

### 4.3 系统强制规则

| 规则 | 触发条件 | 行为 |
|------|----------|------|
| DRAFT 无法评审 | 文档状态=DRAFT | 拒绝并提示 |
| ARCHIVED 无法修改 | 文档状态=ARCHIVED | 拒绝并提示 |
| 不允许部分评审 | 评审范围≠完整文档 | 拒绝并提示 |
| todowrite 必须同步 | 任何 todo 操作 | 自动同步到文件 |

## 5. 功能缺失与解决方案

### 5.1 缺失功能识别

| 缺失功能 | 问题 | 影响 |
|----------|------|------|
| 角色边界检查 | Agent1 可以触碰设计/代码 | 职责混乱 |
| 文档状态绑定 | DRAFT 可以被评审 | 流程脱节 |
| 完整性门禁 | 可以部分评审需求 | 文档肢解 |
| todowrite 同步 | todo 不同步到文件 | 工具不可用 |

### 5.2 解决方案设计

#### 5.2.1 F-PROC-001.1 角色边界检查

**功能**: 在文件操作前检查 Agent 权限

**实现方式**:
1. 创建 `role_validator.py` 模块
2. 定义 Agent1/Agent2 的权限规则
3. 在 CLI 命令入口处添加权限检查
4. 越权操作直接拒绝

**用户界面**:
```
$ oc-collab design create F-PROC-001
⛔ 权限拒绝: Agent1 无法创建设计文档。
```

#### 5.2.2 F-PROC-001.2 文档状态绑定

**功能**: 在评审前检查文档状态

**实现方式**:
1. 扩展 `workflow.py` 添加状态检查逻辑
2. 定义文档状态机
3. 评审命令入口处添加状态检查
4. DRAFT 状态拒绝评审

**用户界面**:
```
$ oc-collab review start requirements_v2.2.2_DRAFT.md
⛔ 无法评审: 文档状态为 DRAFT。
```

#### 5.2.3 F-PROC-001.3 完整性门禁

**功能**: 不允许部分评审

**实现方式**:
1. 创建 `completeness_guard.py` 模块
2. 评审命令入口处检查评审范围
3. 只允许评审完整文档

**用户界面**:
```
$ oc-collab review start F-AUTO-004 --section-only
⛔ 不允许部分评审，请评审完整文档。
```

#### 5.2.4 F-PROC-001.4 todowrite 同步修复

**功能**: todowrite 操作后自动同步到文件

**实现方式**:
1. 扩展 `auto_engine.py` 的 `TodoCommandExecutor`
2. 添加文件同步逻辑
3. 自动同步到 `state/agent_adhoc_todos.yaml`

**用户界面**:
```
$ oc-collab todo add "新任务" --agent agent1
✓ 已添加任务: TODO-XXX
✓ 已同步到文件: state/agent_adhoc_todos.yaml
```
