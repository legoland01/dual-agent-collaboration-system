## 一、备忘录摘要

本备忘录基于 oc-collab v2.2.0 开发过程中的实践经验，以及与 Agent 2 关于"控制与分布式智能平衡"的深度讨论，总结 oc-collab 的核心设计哲学。

**核心结论**：

1. **约束是必要的**，但必须分层处理
2. **智能是分布式的**，oc-collab 做"守门员"，不做"控制狂"
3. **Agent 能力需要发挥**，技术方案应下放给开发 Agent
4. **质量底线不可破**，L1 约束强制执行

**一句话总结**：

> oc-collab 应该像"教练"而不是"监工"——制定规则、检查关键点、给出建议，但信任运动员（Agent）有自己的跑法。

## 二、背景

### 2.1 两个项目的对比

| 维度 | oc-collab 自身 | Financial 项目 |
|------|----------------|----------------|
| **使用方式** | 原生使用，严格遵循 | 混合使用，跳过签署 |
| **状态管理** | 完整的 state 文件 | 几乎没有 state |
| **里程碑签署** | 严格遵循 | 几乎跳过 |
| **测试覆盖** | 单元测试+E2E+黑盒 | 很少测试 |
| **结果** | 顺畅，里程碑清晰 | 磕磕绊绊，同样的问题重复发生 |

**核心发现**：不是 oc-collab 能否适配项目的问题，而是 Financial 项目**根本没有真正使用 oc-collab**。

### 2.2 反复发生的问题分类

| 问题类型 | 轻易解决 | 迟迟未解决 |
|----------|----------|------------|
| **工具缺失** | 配置验证、模式管理、测试隔离 | — |
| **约束缺失** | 签署流程改进 | 认知免疫系统（v2.2.1） |
| **行为/认知** | — | Agent 忘记协作、独自决策 |

**根本原因**：

> 不是"功能没提供"，而是 Agent 在协作过程中会丢失协作意识。

### 2.3 管理人与管理 Agent 的本质区别

| 对比 | 管理人 | 管理 Agent |
|------|--------|------------|
| 读文档 | 人不会认真读 | Agent 严格执行指令 |
| 写文档 | 人会偷懒 | 任务描述越清晰效果越好 |
| 文档假设 | 人会保持文档最新 | — |

**关键洞察**：Agent 会严格执行指令，这既是优点也是风险。

- **优点**：约束机制可以真正执行
- **风险**：如果约束过严，Agent 会变成"执行器"，浪费其自主能力

## 三、核心问题：控制与分布式智能的平衡

### 3.1 问题本质

```
过度控制 ───────────────────────────── 过度自由
   │                                         │
   │  Agent变成执行器                    Agent各自为政
   │  浪费Agent能力                      混乱
   │                                         │
   │              │                 │
   │              ▼                 ▼
   │         oc-collab单点故障    无法形成合力
```

**最优点**：让 Agent 在约束框架内自主决策。

### 3.2 传统软件工程的假设

| 假设 | 现实 |
|------|------|
| 人会认真写和读文档 | 人会犯懒，文档会过时 |
| 人会保持文档最新 | 人不会 |
| 流程会得到贯彻 | 人会跳过不喜欢的步骤 |

**对 Agent 的新假设**：

| 假设 | 现实 |
|------|------|
| Agent 会严格执行指令 | 是 |
| 任务描述越清晰效果越好 | 是 |
| 需要平衡管理和控制的需求 | 是 |
| 智能集中在一处不是好事情 | 是 |

### 3.3 关键平衡点

**oc-collab 的角色定位**：

| 角色 | 说明 | 例子 |
|------|------|------|
| **规则制定者** | 定义约束、目标、质量标准 | phase 划分、质量门禁 |
| **协调者** | 处理 Agent 之间的切换、状态同步 | switch 命令、状态追踪 |
| **检查者** | 在关键节点验证是否符合要求 | 签署检查、Bug 追踪 |
| **不是** | 所有智能集中在 oc-collab，Agent 只是执行器 | 技术方案不应该由 oc-collab 决定 |

**Agent 的角色定位**：

| 角色 | 说明 | 例子 |
|------|------|------|
| **自主执行者** | 在约束范围内自主决策 | 技术方案选择、实现细节 |
| **专业贡献者** | 发挥各自能力解决问题 | Bug 修复、功能开发 |
| **规则遵循者** | 遵守 oc-collab 的约束和质量标准 | 签署流程、质量检查 |

## 四、设计建议

### 4.1 约束的层级结构

| 层级 | 约束类型 | 强制程度 | 例子 | 理由 |
|------|----------|----------|------|------|
| **L1 法律** | 质量门禁、签署流程 | 🔴 强制 | 未签署不能进入下一 phase | 不可妥协的质量底线 |
| **L2 规则** | phase 切换、里程碑推进 | 🟡 推荐 | 建议走完当前 phase 再开始新需求 | 保持流程完整 |
| **L3 指南** | 命名规范、文件结构 | 🟢 柔性 | 推荐的文件命名格式 | 可适应项目特点 |

**关键原则**：不是所有约束都同等重要，应该分级处理。

### 4.2 决策权的分配

| 决策类型 | 谁决定 | 理由 |
|----------|--------|------|
| 需求变更 | oc-collab (产品 Agent 主导) | 需求是产品 Agent 的职责 |
| 技术方案 | 开发 Agent | 技术能力在开发 Agent |
| 流程合规 | oc-collab | 系统规则，不容妥协 |
| 执行细节 | 开发 Agent | 信任专业能力 |

**一句话原则**：

> oc-collab 管"做什么"和"做到什么标准"，Agent 管"怎么做"。

### 4.3 动态平衡机制

固定分配有问题，应该根据场景动态调整：

| 场景 | Agent 自主度 | oc-collab 介入度 | 说明 |
|------|-------------|-----------------|------|
| 核心模块修改 | 低 | 高 | 强制评审 |
| 辅助功能开发 | 高 | 低 | 信任 |
| Bug 修复 | 中 | 中 | 检查是否历史问题 |
| 新需求引入 | 低 | 高 | 必须走评审 |

### 4.4 Agent 切换的管理

**核心问题**：Agent 模式切换带来的管理负担。

**观察**：

- Agent 切换有认知负荷，单一 Agent 维护多套上下文容易混淆
- Compaction 时，模式状态可能丢失

**建议架构**：主 Agent + 专业 Agent 模式

```
┌─────────────────────────────────────────────────────┐
│  主 Agent (当前 Agent)                               │
│  ├── 职责：需求理解、方案设计、协调                    │
│  └── 状态：当前迭代目标                               │
└─────────────────────────────────────────────────────┘
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
   ┌──────────┐    ┌──────────┐    ┌──────────┐
   │Bug Agent │    │Dev Agent │    │Test Agent│
   │(按需调度)│    │(按需调度)│    │(按需调度)│
   └──────────┘    └──────────┘    └──────────┘
          │               │               │
          └───────────────┴───────────────┘
                          │
                          ▼
               ┌─────────────────────┐
               │ 状态同步到 oc-collab │
               │ (所有 Agent 可见)    │
               └─────────────────────┘
```

**关键机制**：

| 机制 | 说明 |
|------|------|
| **主 Agent 不变** | 需求理解、迭代目标由同一个 Agent 维护 |
| **专业 Agent 按需调度** | Bug 修复、测试执行等由临时 Agent 处理 |
| **状态同步** | 所有 Agent 的工作结果同步到 oc-collab state |
| **模式门禁** | 专业 Agent 只能在当前 mode（phase）下工作 |

## 五、关键问题与建议

### 问题 A：L2 约束如何执行？

**选项**：

| 选项 | 说明 | 优缺点 |
|------|------|--------|
| 软强制 | 不遵守则警告，但允许继续 | 灵活但可能无效 |
| 延迟强制 | 允许继续，但在 phase 切换时强制处理 | 平衡灵活性和约束 |
| 解释机制 | 不遵守需要说明理由，记录在案 | 可追溯、有反馈 |

**建议**：选项 2 + 选项 3 组合

> 允许在 L2 约束上有灵活性，但在 phase 切换时必须处理未遵守的约束，并说明理由。

### 问题 B：Agent 觉得约束不合理怎么办？

**选项**：

| 选项 | 说明 | 优缺点 |
|------|------|--------|
| 可以申诉 | Agent 说明理由，由产品 Agent 决定是否豁免 | 灵活但可能滥用 |
| 不可豁免 | 规则就是规则，必须遵守 | 严格但可能不合理 |
| 定期复盘 | 收集 Agent 反馈，调整约束规则 | 长期优化但短期问题 |

**建议**：选项 1 + 选项 3 组合

> 允许紧急情况下的豁免申诉，同时建立定期复盘机制收集反馈。

### 问题 C：如何避免 oc-collab 成为单点故障？

**选项**：

| 选项 | 说明 | 优缺点 |
|------|------|--------|
| 规则外置 | 约束规则可配置、可审计 | 灵活但复杂 |
| Agent 投票 | 重大决策由 Agent 集体判断 | 民主但可能低效 |
| 人机混合 | 关键决策需要真人确认 | 安全但增加人工成本 |

**建议**：选项 1 + 选项 3 组合

> 约束规则外置、可配置，同时关键决策保留人工确认入口。

## 六、最终建议

### 6.1 核心原则

| 原则 | 说明 |
|------|------|
| **约束分层** | L1 强制、L2 推荐、L3 柔性，三层清晰区分 |
| **决策下放** | 技术方案、执行细节交给 Agent |
| **智能检查** | oc-collab 做"守门员"，不做"控制狂" |
| **反馈闭环** | Agent 可以反馈约束不合理之处 |

### 6.2 一句话总结

> oc-collab 应该像"教练"而不是"监工"——制定规则、检查关键点、给出建议，但信任运动员（Agent）有自己的跑法。
