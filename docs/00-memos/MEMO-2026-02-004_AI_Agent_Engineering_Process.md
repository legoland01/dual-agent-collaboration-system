## 一、问题起点

### 1.1 问题描述

在 v2.2.0 需求文档（requirements_v2.2.0.md）中，有一项需求描述如下：

| 需求编号 | 需求名称 | 描述 |
|----------|----------|------|
| FR-MEMORY-003 | 周期性回顾提醒 | 每次会话开始时显示"上次会话遗留问题: 3个" |

但在 v2.2.0 交付时，该功能**未被实现**。

### 1.2 问题的暴露

2026-02-03，在与 Financial Case Generator System 项目 Agent 1 的对话中发现：该 Agent 不知道 oc-collab 的存在，不知道自己的角色（Agent 1 vs Agent 2），不知道应该遵循什么流程。

这直接证明了 **session_start** 功能缺失导致的严重后果：Agent 在新会话中无法获得必要的上下文信息，导致协作混乱。

### 1.3 问题定性

| 属性 | 值 |
|------|-----|
| 问题类型 | 流程缺陷 |
| 严重程度 | P0 - 核心流程缺失 |
| 影响范围 | 所有使用 oc-collab 的项目 |
| v2.2.0 状态 | 已签署发布，但功能缺失 |

## 三、根因分析（5-Why 分析）

### Why 1：为什么功能缺失？

**现象**：session_start 需求写在需求文档中，但代码中没有实现。

**直接原因**：
- 需求文档有描述（FR-MEMORY-003）
- 设计文档没有对应设计
- 测试文档没有对应用例
- 代码没有实现

### Why 2：为什么设计和测试都没有？

**现象**：需求写了，但设计评审和测试评审都跳过了这个需求。

**直接原因**：
- 需求文档中的描述不够明确，无法直接转化为设计
- FR-MEMORY-003 被归类为"记忆功能"，不是独立功能
- 评审时没有检查"需求→设计→代码"的追溯关系

**关键发现**：需求文档中 session_start 只是"提醒配置"的一部分，没有独立的需求编号和详细描述。

### Why 3：为什么评审流程没有发现？

**现象**：需求评审、设计评审、测试评审都签署了，但没有人发现缺失。

**直接原因**：
- oc-collab 的评审是"文档存在性检查"，不是"功能完整性检查"
- 评审者检查"文档格式是否正确"、"内容是否完整"，但没有检查"是否可追溯到代码"
- 签署流程没有"功能验证"环节

**关键发现**：oc-collab 的签署是"走形式"，只验证文档存在，不验证功能实现。

### Why 4：为什么 oc-collab 的流程是"文档存在性检查"？

**现象**：评审只检查文档，不验证功能。

**设计假设**：
- oc-collab 假设有"人"在监督整个流程
- 人会主动检查功能是否实现
- 但实际上 Agent 在评审时只是"读文档"，没有"验证功能"的机制

**关键发现**：oc-collab 的流程设计基于"人会主动发现问题"的假设，但这个假设在 AI Agent 场景下不成立。

### Why 5（根本原因）：oc-collab 的流程是为人设计的，不是为 AI Agent 设计的

| 设计假设 | 人 | AI Agent |
|----------|---|----------|
| 会主动检查 | ✅ | ❌ |
| 会记住教训 | ✅ | ❌ (Compaction 会丢失) |
| 会理解上下文 | ✅ | ❌ (每次 session 独立) |
| 会质疑不完整 | ✅ | ❌ (只执行指令) |

**根本原因**：

> oc-collab 试图用"人的协作方式"来约束 AI Agent，但 AI Agent 的行为模式与人完全不同。
>
> 人会主动发现问题、质疑不完整、理解上下文。
> AI Agent 只执行指令、遵循表面规则、不会主动验证。

### 系统性问题总结

| 问题 | 表现 | 影响 |
|------|------|------|
| **流程假设错误** | 用人的行为假设设计 AI Agent 流程 | 流程无法约束 AI |
| **签署虚假** | 只验证文档存在，不验证功能 | 签署形同虚设 |
| **追溯缺失** | 需求→设计→代码无关联 | 功能可能丢失 |
| **验证缺失** | 没有功能测试环节 | Bug 无法发现 |

## 四、建议的解决方案

### 4.1 核心设计原则

基于根本原因，AI Agent 软件工程流程必须遵循以下原则：

| 原则 | 说明 | vs 传统流程 |
|------|------|-------------|
| **强制约束 > 建议约束** | 不是"建议做"，而是"必须做" | 传统流程依赖人自觉 |
| **系统自动验证 > 人检查** | 系统自动发现问题和缺失 | 传统流程依赖人检查 |
| **追溯关联 > 独立文档** | 强制关联需求-设计-代码-测试 | 传统流程文档独立 |
| **记忆持久化 > 依赖记忆** | 强制记录，自动加载 | 传统流程依赖人记忆 |

### 4.2 强制约束架构

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 4: 签署约束                                           │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ - 功能验证通过前不能签署                               │   │
│  │ - 签署必须关联需求 ID                                  │   │
│  │ - 签署必须通过自动检查（需求-设计-代码-测试完整性）     │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
                            ▲
┌─────────────────────────────────────────────────────────────┐
│  Layer 3: 测试约束                                           │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ - 没有需求关联不能编写测试                              │   │
│  │ - 测试必须覆盖所有需求                                  │   │
│  │ - 测试失败不能提交代码                                  │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
                            ▲
┌─────────────────────────────────────────────────────────────┐
│  Layer 2: 代码约束                                           │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ - 代码提交必须关联需求 ID                               │   │
│  │ - 没有设计文档不能编写代码                               │   │
│  │ - 代码必须通过 lint + typecheck                         │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
                            ▲
┌─────────────────────────────────────────────────────────────┐
│  Layer 1: 需求约束                                           │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ - 需求必须有唯一 ID                                    │   │
│  │ - 需求必须有验收标准                                    │   │
│  │ - 需求必须有设计对应                                    │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 关键机制设计

#### 机制1：需求-代码追溯

**约束**：每个代码提交必须包含追溯信息。

```
提交信息模板：
<type>(<scope>): <description>

[body]
requirements_id: <需求ID>
design_id: <设计文档ID>
test_id: <测试用例ID>

[footer]
```

**强制执行**：如果没有这些字段，Git 提交被拒绝。

#### 机制2：自动功能验证

**约束**：签署前必须通过自动验证。

```
签署前检查清单：
┌───────────────────────────────────────────────┐
│ □ 需求是否有对应代码？                         │
│   - 检查: 代码文件中是否包含 requirements_id   │
│                                                     │
│ □ 代码是否有对应测试？                         │
│   - 检查: 测试文件中是否包含 requirements_id    │
│                                                     │
│ □ 测试是否通过？                               │
│   - 运行: pytest --tb=short                      │
│                                                     │
│ □ 测试覆盖率是否达标？                         │
│   - 检查: coverage >= 80%                        │
└───────────────────────────────────────────────┘
```

**强制执行**：任何一项不通过，签署被阻止。

#### 机制3：会话起始引导（session_start）

**约束**：Agent 新会话开始时，系统自动显示上下文信息。

```
┌─────────────────────────────────────────────────────────────┐
│  === Agent 2 (开发负责人) ===                               │
│                                                             │
│  当前项目: dual-agent-collaboration-system                   │
│  当前阶段: requirements_review                               │
│  当前里程碑: v2.2.1                                          │
│                                                             │
│  你的职责:                                                  │
│    - 评审需求文档                                            │
│    - 编写详细设计                                            │
│    - 签署确认                                                │
│                                                             │
│  待办事项:                                                  │
│    [ ] 评审 requirements_v2.2.1_DRAFT.md                    │
│    [ ] 签署需求确认                                          │
│                                                             │
│  上次会话遗留:                                              │
│    - BUG-20260202-001 待实现                                │
│                                                             │
│  常用命令:                                                  │
│    - oc-collab status    查看状态                           │
│    - oc-collab review    评审                               │
│    - oc-collab signoff   签署                               │
└─────────────────────────────────────────────────────────────┘
```

**强制执行**：每次 `oc-collab status` 或切换 Agent 时自动显示。

#### 机制4：记忆持久化

**约束**：所有决策、问题、教训必须持久化到独立文件。

```
state/memory/
├── decisions.yaml      # 决策历史
├── problems.yaml       # 问题模式库
├── lessons.yaml        # 经验教训
└── pending.yaml        # 待处理事项

Compaction 前检查：
  - 是否已导出所有 memory 文件？
  - memory 文件是否有签名？
  - 签名是否有效？
```

**强制执行**：Compaction 前必须通过记忆完整性检查。

### 4.4 流程改进清单

| 改进项 | 当前状态 | 目标状态 | 优先级 |
|--------|----------|----------|--------|
| 需求追溯 | 无 | 需求ID强制关联 | P0 |
| 设计追溯 | 无 | 设计ID强制关联 | P0 |
| 测试追溯 | 无 | 测试ID强制关联 | P0 |

| 会话引导 | 无 | 新会话自动显示 | P0 |

## 六、结论

### 6.1 核心发现

oc-collab v2.2.0 的 session_start 功能缺失，不是简单的"遗漏"，而是**流程假设的根本错误**：

> oc-collab 用"人的协作方式"设计 AI Agent 流程，但 AI Agent 不会主动检查、不会主动验证、不会主动发现缺失。

### 6.2 解决方向

AI Agent 软件工程流程必须遵循"**强制约束 + 系统验证 + 追溯关联 + 记忆持久化**"的设计原则。
