# 讨论纪要：测试平台与测试用例跟踪系统

**日期**: 2026-02-17  
**参与**: Agent 1  
**主题**: 测试平台需求讨论

---

## 用户需求汇总

### 1. 核心问题
- 测试用例设计 ≠ 测试执行，缺乏跟踪机制
- Bug漏到生产环境（ACK命令bug）
- 需要防控"虚假测试"和"collusion"（自己测自己的代码）

### 2. 测试平台定位
- 所有模块部署完成后，在集成环境中测试
- 模块间深度依赖，必须在真实环境中验证

### 3. 测试平台能力需求

| 需求 | 说明 |
|------|------|
| 前端页面互动 | Web界面进行测试，而不是纯命令行 |
| 页面截图对比 | 测试前/后截图验证 |
| 智能页面验证 | 解读页面内容，判断是否符合预期 |
| 沙盒隔离 | 测试数据不污染生产系统 |
| 环境部署条件管理 | 事先确定测试前置条件 |

### 4. 测试用例跟踪（数据库化）

| 需求 | 说明 |
|------|------|
| 测试用例数据库化 | 每个用例记录到数据库 |
| 执行记录追溯 | 谁、何时、执行了什么、结果如何 |
| 关联Bug | 测试执行记录关联Bug ID |
| 防Collusion | 记录执行人，防止自己测自己 |

### 5. 自动Bug流程

```
测试失败 → 自动创建Bug → 自动创建修复TODO → 修复后自动验证 → 通过自动关闭Bug
```

## Agent 1 输入/观点

### 观点1：测试分类建议

我认为测试应该分层次：

| 类型 | 范围 | 频率 | 平台要求 |
|------|------|------|----------|
| 单元测试 | 单个函数/模块 | 每次提交 | 本地即可 |
| E2E测试 | 完整功能流程 | 每次发布 | **测试平台** |
| 冒烟测试 | 核心功能 | 每次部署 | 测试平台 |

**理由**：不同层次测试对环境要求不同，不需要所有测试都在平台上跑。

### 观点2：智能页面验证的实现路径

用户提到"解读页面内容并作出实质性判断"，我认为可以：
- 使用LLM解读页面截图/内容
- 或使用规则引擎（用户提到的verify_rules）

**建议**：先用规则引擎（简单可控），LLM作为进阶能力。

### 观点3：关于测试独立性的补充

用户强调防collusion，我补充一个视角：

| 角色 | 建议 |
|------|------|
| Agent1设计测试 | Agent2执行 |
| Agent2开发功能 | Agent1执行测试 |

这样可以真正做到"开发与测试分离"。

### 观点4：渐进式实施

我认为可以分阶段：

| 阶段 | 目标 |
|------|------|
| Phase 1 | 测试用例数据库化 + 执行记录 |
| Phase 2 | 前端页面互动 |
| Phase 3 | 智能验证 + 自动Bug流程 |
| Phase 4 | LLM辅助验证 |

**理由**：一下子做太多会增加风险，渐进式可以快速迭代。
