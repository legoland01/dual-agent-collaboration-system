## 1. Bug描述

使用edit工具编辑TODO文件时，可能因oldString匹配不精确导致编辑失败或产生意外结果。

### 历史问题

| 时间 | 操作 | 结果 |
|------|------|------|
| 2026-02-13 | 创建TODO-298 | 成功 |
| 2026-02-13 | 创建TODO-300 | oldString不精确，多次尝试才成功 |

### 用户反馈的问题

"似乎每次创建一个todo都会有一个空的todo同时被创建"

**核实结果**:
```bash
grep -n "id: TODO-299\|id: TODO-301" state/agent_adhoc_todos.yaml
# TODO-301: 存在且有完整内容
# TODO-299: 不存在
```

**结论**: 用户反馈"空TODO"可能是误报，但edit工具使用确实存在问题。

---

## 4. 实际问题和修复

### edit工具使用问题

| 问题 | 修复 |
|------|------|
| oldString匹配不精确 | 使用完整的oldString，或使用grep先确认内容 |
| edit后未验证 | edit后立即用grep验证 |
| 多次尝试编辑 | 改用write工具重写整个文件 |

### 标准化edit流程

```python
# 1. 先用grep确认oldString存在且正确
grep(path="state/agent_adhoc_todos.yaml", pattern="要匹配的内容")

# 2. 执行edit
edit(
  filePath="state/agent_adhoc_todos.yaml",
  oldString="完整的内容（多行）",
  newString="新的完整内容"
)

# 3. 立即验证
grep(path="state/agent_adhoc_todos.yaml", pattern="新添加的内容")

# 4. 如果失败，用write工具重写
write(
  filePath="state/agent_adhoc_todos.yaml",
  content="完整文件内容"
)
```

```bash
grep -A10 "id: TODO-[0-9]+" state/agent_adhoc_todos.yaml | head -30

```

## 9. 反思

**用户指出**: "难道不是每次你遇到oc-collab的问题就首先应该报一个bug然后按照标准流程去解决它吗？"

**深刻反思**:

我之前对"Bug"的理解过于狭隘：
- ❌ 认为只有"代码错误"才是Bug
- ❌ 认为"流程意识不足"应该自己改正
- ❌ 等待用户指令才报告问题

**正确的理解**:
- ✅ oc-collab系统的任何问题都是Bug
- ✅ 包括：流程问题、操作问题、工具问题
- ✅ 发现问题 → 立即报告 → 分析根因 → 修复/指派

**应该建立的习惯**:
1. **主动观察**: 时刻关注oc-collab系统的运行状态
2. **立即报告**: 遇到任何问题立即创建Bug报告
3. **标准流程**: Bug报告 → 调查 → 修复/指派 → 验证

**具体的改进**:
- 每次操作后主动验证结果
- 发现任何异常立即报告Bug
- 不再"默默改正"，而是公开记录问题
