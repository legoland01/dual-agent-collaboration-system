## 一、5-Why 分析修正

### 原始分析的问题

原始分析中说"人会主动发现问题"，这是一个**错误的假设**。

### 实际观察到的事实

| 角色 | 行为模式 |
|------|----------|
| 人 | 会偷懒、应付、走形式、跳过不喜欢的步骤 |
| AI Agent | 会严格执行指令，但只做被明确要求的事 |

### 核心洞察（修正后）

> AI Agent 的优势不是"不会偷懒"，而是"控制机制得当就能确保执行"。
> 
> 人的问题是"机制再完善也会绕过"。
> AI 的问题是"机制不完善就不知道做什么"。
> 
> 因此，解决方案不是"让 AI 更主动"，而是"让机制更完善"。

## 二、动态 Checklist 机制设计

### 2.1 核心概念

**动态 Checklist**：根据评审对象的实际内容，由 oc-collab 自动生成针对性的检查项。

**vs 静态 Checklist**：
- 静态：所有人、所有项目都是同一份检查表
- 动态：根据文档内容自动生成针对性的问题

### 2.2 工作原理

```
┌─────────────────────────────────────────────────────────────┐
│  评审者（Agent 1 或 Agent 2）                                │
│                                                             │
│  1. 执行评审命令                                             │
│     oc-collab review requirements --file requirements_v2.md │
│                                                             │
│  2. oc-collab 分析文档内容                                   │
│     - 提取所有需求                                           │
│     - 识别依赖关系                                           │
│     - 生成动态 checklist                                     │
│                                                             │
│  3. 显示 checklist 和文档                                    │
│     Agent 逐项检查并记录结果                                 │
│                                                             │
│  4. 系统验证所有 checklist 是否完成                          │
│     - 未完成的检查项不允许签署                               │
└─────────────────────────────────────────────────────────────┘
```

### 2.4 动态 checklist 生成逻辑

```python
def generate_review_checklist(document_path: str, document_type: str) -> Checklist:
    """
    根据文档内容动态生成评审 checklist
    """
    checklist = []
    
    # 1. 基础检查（所有文档通用）
    checklist.extend([
        CheckItem("格式正确", "文档格式符合模板要求"),
        CheckItem("版本信息", "文档包含版本号和更新日期"),
        CheckItem("完整性", "所有章节内容完整"),
    ])
    
    # 2. 需求文档专项检查
    if document_type == "requirements":
        requirements = extract_requirements(document_path)
        for req in requirements:
            checklist.extend([
                CheckItem(f"需求 {req.id} - 唯一ID", "需求是否有唯一标识"),
                CheckItem(f"需求 {req.id} - 验收标准", "需求是否有明确的验收标准"),
                CheckItem(f"需求 {req.id} - 详细描述", "需求描述是否完整"),
                CheckItem(f"需求 {req.id} - 设计关联", "是否有对应的设计文档"),
                CheckItem(f"需求 {req.id} - 测试关联", "是否有对应的测试用例"),
            ])
    
    # 3. 设计文档专项检查
    if document_type == "design":
        checklist.extend([
            CheckItem("需求关联", "设计是否关联到具体需求"),
            CheckItem("实现方案", "实现方案是否具体可行"),
            CheckItem("边界条件", "是否覆盖所有边界情况"),
        ])
    
    # 4. 检查追溯关系
    if document_type in ["requirements", "design"]:
        # 检查是否存在未关联的需求/设计
        orphan_items = find_orphan_items(document_path)
        if orphan_items:
            checklist.append(CheckItem(
                "追溯性",
                f"发现 {len(orphan_items)} 个未关联的条目，需要处理"
            ))
    
    return checklist
```

## 三、评审流程改进

### 3.1 改进后的评审流程

```
传统流程（问题）          改进流程（方案）
─────────────────         ─────────────────
Agent 读文档              Agent 读文档 + Checklist
↓                         ↓
Agent 随意检查            系统强制检查每项
↓                         ↓
Agent 签字                系统验证所有项通过
↓                         ↓
签署完成                  缺失项必须解决后才能签署
```

### 3.2 评审命令改进

```bash
# 传统方式
oc-collab review requirements --file requirements_v2.md
# 结果：只显示文档，评审者自己决定检查什么

# 改进方式
oc-collab review requirements --file requirements_v2.md --checklist
# 结果：显示文档 + 动态 checklist + 系统验证
```

### 3.3 签署前置条件

```
签署前必须满足：
  1. 所有需求评审 checklist 通过
  2. 所有设计评审 checklist 通过
  3. 所有测试用例存在并通过
  4. 测试覆盖率 >= 80%

任何一项不通过，签署被阻止：
❌ 无法签署：需求评审存在未通过项
   - FR-MEMORY-003: 需求描述不完整
   - FR-MEMORY-003: 没有对应设计文档
```
