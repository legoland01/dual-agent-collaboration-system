## 2. 讨论议题与决策

### 2.1 资源锁定超时后处理机制

**问题陈述**:
当资源锁超时（30分钟）后，系统应该如何处理？

**讨论方案**:

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| 方案A | 自动释放锁，不通知任何人 | 简单 | 可能导致工作丢失 |
| 方案B | 自动释放锁，通知项目经理 | 平衡 | 需要项目经理介入 |
| 方案C | 不自动释放，人工干预 | 安全 | 可能导致死锁 |

**最终决策**: 方案B（分层通知 + 自动降级）

**详细处理流程**:
```
超时流程：
1. 提前5分钟警告（Git Comment/锁持有者）
2. 超时后 → 自动释放锁
3. → 通知Agent 1（项目经理）
4. → 任务状态改为 "BLOCKED"
5. → Agent 1决定：重新分配 或 等待原Agent
```

**理由**:
- 自动化程度高，避免死锁
- 保留人工决策权（Agent 1 作为 PM 有权重新调整架构）
- 5分钟提前警告给 Agent 缓冲时间

### 2.2 任务依赖循环检测

**问题陈述**:
当任务依赖形成循环（A依赖B，B依赖A）时，系统如何处理？

**讨论方案**:

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| 方案A | 创建时检测，阻止循环 | 提前发现 | 可能过于严格 |
| 方案B | CI/PR时检测，阻止合并 | 成本最低 | 发现较晚 |
| 方案C | 只警告，不阻止 | 灵活 | 可能遗漏 |

**最终决策**: 方案B（CI时阻止 + Agent 1 介入）

**详细处理流程**:
```
检测时机：PR/MR提交时
处理流程：
1. 发现循环依赖 → 阻止合并
2. 在PR中标记冲突任务
3. 通知Agent 1和涉及的Agent
4. Agent 1负责解环（重新设计依赖）
```

**理由**:
- CI 阶段拦截成本最低
- Agent 1 作为 PM 有权重新调整架构
- 在 PR 中标记可以清晰展示问题

### 2.3 多代理协调通知机制

**问题陈述**:
Agent 间协调通知应该使用什么机制？

**讨论方案**:

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| 方案A | 仅 Git 层（Comment/Commit） | 简单、可追溯 | 实时性差 |
| 方案B | 仅即时层（Slack/邮件） | 实时性强 | 不可追溯 |
| 方案C | 双层机制（Git + Webhook） | 平衡 | 复杂度较高 |

**最终决策**: 方案C（双层通知机制）

**通知层级设计**:

| 层级 | 方式 | 用途 | 重要事件 |
|------|------|------|----------|
| **Git层** | Comment/Commit消息 | 正式协作记录，可追溯 | 所有事件 |
| **即时层** | 可配置Webhook | Slack/邮件/飞书（仅重要事件） | 锁超时、循环依赖、阻塞、评审请求 |

**推荐的重要事件（Webhook通知）**:
- 锁超时释放
- 循环依赖检测
- 任务完成/阻塞
- PR评审请求

**理由**:
- Git 保证可追溯性
- 即时通知保证效率
- Webhook 可插拔设计灵活
- 可配置性满足不同团队需求

### 2.4 任务分配粒度设计

**问题陈述**:
任务分配应该使用什么粒度？

**讨论方案**:

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| 方案A | 单层（Task） | 简单 | 缺少上层视角 |
| 方案B | 两层（Feature + Task） | 清晰 | 缺少用户故事 |
| 方案C | 三层（Epic + Story + Task） | 完整敏捷 | 复杂度高 |

**初步讨论**:
- Agent 2 提出三层粒度（Epic/Story/Task）
- Agent 1 质疑：Task 是否可以同时隶属于 Epic 和 Story？

**问题发现**:
Agent 2 初始表述有误，Task 不应同时隶属于 Epic 和 Story。

**修正后的层级关系**:
```
┌─────────────────────────────────────────┐
│ Epic (功能模块) - Agent 1创建            │
│   ├── Story (用户故事) - Agent 1创建     │
│   │       └── Task (技术任务) ← 仅隶属于Story │
│   └── Story (用户故事) - Agent 1创建     │
│           └── Task (技术任务) ← 仅隶属于Story │
└─────────────────────────────────────────┘
```

**最终决策**: 方案B（两层粒度：Feature + Task）

**推荐命令**:
```bash
# 分配 Feature（必须指定）
oc-collab project assign --task "实现JWT" --feature "用户登录" --agent backend

# 查看任务
oc-collab project tasks --agent backend
```

**理由**:
1. oc-collab 是**开发者工具**，不是产品管理工具
2. Agent 2 是开发 Lead，关注技术任务即可
3. 保持简单，降低维护成本
4. Feature 足以作为任务的父级容器

## 3. 决策总结

| 议题 | 最终决策 | 复杂度 |
|------|----------|--------|
| 资源锁超时 | 分层通知 + 自动释放 + Agent 1介入 | 中 |
| 循环依赖检测 | CI阻止 + Agent 1介入解环 | 低 |
| 通知机制 | Git层 + Webhook双层（可配置） | 中 |
| 任务粒度 | 两层（Feature + Task） | 低 |
