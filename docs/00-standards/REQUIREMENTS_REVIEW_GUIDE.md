# OC-Collab 需求评审指南

## 1. 角色职责分工

| 角色 | 职责 | 产出物 |
|------|------|--------|
| **Agent 1** | 产品经理 | 需求文档、黑盒测试、验收签署 |
| **Agent 2** | 开发 | 设计文档、代码实现、白盒测试 |

### 常见错误

| 错误 | 正确做法 |
|------|---------|
| Agent 1 创建设计文档 | Agent 2 创建设计文档 |
| Agent 2 编写黑盒测试 | Agent 1 编写黑盒测试 |
| 单人签署 | 必须双签 |

---

## 2. 实质性评审检查项

Agent 2 评审需求时，**禁止**只写"✅ 通过"，必须回答：

### 2.1 技术可行性

- [ ] 这个功能在当前架构下能实现吗？
- [ ] 有没有技术风险没识别出来？
- [ ] 实现复杂度是否被低估了？

### 2.2 完整性

- [ ] 验收标准是否可测试？
- [ ] 异常流程是否覆盖了？
- [ ] 有没有遗漏的边界条件？

### 2.3 可实施性

- [ ] 工时预估是否合理？
- [ ] 依赖关系是否正确？
- [ ] 需要额外依赖吗？

### 2.4 逆向思考（必须）

- [ ] **如果我是用户，这个设计好用吗？**
- [ ] **最大的风险点是什么？**
- [ ] **有没有更好的实现方式？**

---

## 3. 评审输出格式

### 错误示例（❌ 走形式）

```
评审结果: ✅ 通过
签署: Agent 2 2026-02-08
```

### 正确示例（✅ 实质性）

```
评审结果: ✅ 通过（带具体意见）

技术可行性:
- 实现方案可行
- ⚠️ 建议: .a 文件解析建议用现有 YAML 解析器

完整性:
- 验收标准完整
- ✅ 已覆盖正常和异常流程

可实施性:
- 工时 5h 合理
- 无额外依赖

逆向意见:
- status 显示待办条数限制 5 条可能不够
- 建议改为分页或滚动显示
```

---

## 4. 评审未通过的处理

| 情况 | 处理 |
|------|------|
| 小问题 | Agent 1 修复后重新提交 |
| 大问题 | 打回重做，标记 DRAFT |

**禁止**: 明知有问题还说"✅ 通过"

---

## 5. 签署规范

| 角色 | 签署内容 | 禁止 |
|------|---------|------|
| Agent 1 | "创建需求" / "发起评审" | 签署"评审通过" |
| Agent 2 | "技术评审通过" | 签署"创建" |
