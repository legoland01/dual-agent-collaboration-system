# AI Agent 时代的人机协同软件工程：一次深度探索

---

## 摘要

本文记录了一次针对 AI Agent 软件工程实践的系统性探索。通过一个具体案例研究——在 oc-collab 项目中发现并分析一个功能缺失问题——我们展示了人机协作如何揭示传统软件工程中的根本性假设，并提出改进方法论。

这次探索最重要的收获不在于技术方案，而在于揭示了**人机协作模式中人类的核心价值**：人类可能不关注技术细节，但拥有足够的常识和判断力，能够直击问题核心，引导 AI 走向更有价值的方向。

## 摘要（浓缩版）

本文记录了一次针对 AI Agent 软件工程实践的系统性探索，通过 oc-collab 项目中"session_start"功能缺失的真实案例，展示人机协作如何发现并修正传统软件工程中的根本性假设。

**核心发现**：AI Agent 需要与传统人类开发者完全不同的流程控制，这不是因为 AI Agent 能力不足，而是因为它们基于"精确执行明确指令"的范式运作，传统的"期望人主动发现问题"假设在 AI 场景下完全不成立。

**关键转折**：最初的 5-Why 分析得出"人会主动发现问题，AI 不会"的结论，但被人类专家质疑——"人就一定会主动发现问题吗？"这个质疑引导我们找到真正的根因：不是 AI 不如人会主动，而是机制必须从"期望主动"转变为"强制执行"。

**人类核心价值**：在 AI 时代，人类不可替代的价值不在于执行技术任务，而在于**质疑隐含假设、直击问题核心、引导 AI 走向正确方向**。

**解决方案**：提出四项核心原则（强制约束、系统自动验证、追溯关联、持久化记忆）和动态 checklist 机制，确保 AI Agent 工作流程的完整性和可追溯性。

## 背景简介

### oc-collab 是什么

oc-collab 是一个**双 Agent 协作开发框架**，用于协调两个 AI Agent（产品经理 Agent 1 + 开发 Agent 2）共同完成软件项目。它借鉴传统软件工程的阶段划分（需求→设计→开发→测试→部署），通过里程碑签署、质量门禁、状态管理等机制，确保开发过程规范化。

### v2.2.0 核心功能

| 功能 | 说明 |
|------|------|
| 双 Agent 角色管理 | Agent 1（产品）+ Agent 2（开发），职责分离 |
| 里程碑签署 | 每个阶段完成后需双方签字确认 |
| 状态管理 | 记录项目当前 phase、签署状态、待办事项 |
| 记忆机制 | 记录决策、问题模式、经验教训 |

### 极其简单的使用流程

```bash
# 1. 初始化项目
oc-collab init myproject

# 2. 创建需求文档
编辑 docs/01-requirements/requirements_v*.md

# 3. 评审并签署
oc-collab signoff requirements

# 4. 推进到下一阶段
oc-collab advance -p design
```

详细背景资料请见本文档末尾的"附录：oc-collab 项目背景"。

## 第一章：问题的起点

### 1.1 一个沉默的失败

2026 年 2 月，在与一个金融文档生成系统项目中的 AI Agent 进行常规对话时，我们发现了一个令人担忧的问题：该 Agent 对其应该使用的协作框架（oc-collab）毫无认知。当被问及项目工作流程时，该 Agent 的回答仿佛它在独立工作，浑然不知本应存在的角色定义、阶段转换或质量门禁。

这不是一个小的疏漏，而是项目流程控制中的根本性崩溃。

### 1.2 缺失的功能

调查后，我们发现 oc-collab 的 v2.2.0 需求文档中有一个名为 "session_start" 的功能，旨在在每次会话开始时为 Agent 提供上下文信息。需求文档中写道：

> "每次会话开始 | Agent 启动 | '上次会话遗留问题: 3个'"

然而，当我们检查交付的产品时，这个功能并不存在。没有设计文档，没有测试用例，没有实现代码——什么都没有。需求存在，但功能不存在。

### 1.3 为什么这很重要

这不仅仅是一个待修复的 bug，而是一个更深层问题的症状：

- 如果需求可以写下但永远不被实现，流程就已经坏了
- 如果多个评审阶段（需求评审、设计评审、测试评审、签署）都能在不发现这个缺失的情况下完成，评审就毫无意义
- 如果一个核心功能的缺失能直到 Agent 的随意评论才被发现，质量控制机制就是虚幻的

问题不再是"我们如何修复这个 bug？"，而是"我们的整个流程怎么会没能防止这种情况？"

## 第三章：5-Why 分析的修正——人机协作的核心价值

### 3.1 第一次 5-Why 分析（错误版本）

我最初进行了 5-Why 分析，得到的"根因"是：

> "oc-collab 用'人的协作方式'设计 AI Agent 流程，但 AI Agent 不会主动检查、不会主动验证、不会主动发现缺失。"

这个分析的隐含假设是："人会主动发现问题，AI 不会。"

### 3.2 人类专家的质疑

你指出了我分析中的根本性错误：

> "实际上人就一定会主动发现问题吗？我们从实践角度看，是不是大多数时候，人更加会偷懒、应付、走形式？实际上绝大多数流程不就是为了控制这些可能性吗？"

这是一个极其深刻的质疑。它揭示了我分析中的根本性错误假设。

### 3.3 真正的洞察

经过讨论，我们共同修正了分析。真正的洞察是：

| 角色 | 行为模式 |
|------|----------|
| 人 | 会偷懒、应付、走形式、跳过不喜欢的步骤 |
| AI Agent | 会严格执行指令，但只做被明确要求的事 |

**核心结论**：

> AI Agent 的优势不是"不会偷懒"，而是"控制机制得当就能确保执行"。
> 
> 人的问题是"机制再完善也会绕过"。
> AI 的问题是"机制不完善就不知道做什么"。
> 
> 因此，解决方案不是"让 AI 更主动"，而是"让机制更完善"。

### 3.4 人类的核心价值

这次修正揭示了人机协作模式中**人类的核心价值**：

- **人类可能不关注技术细节**，但拥有足够的常识和判断力
- **人类能够直击问题的核心**，而不是迷失在技术细节中
- **人类能够质疑隐含的假设**，而 AI 只会接受并执行

在这次探索中，你（人类专家）没有关注 grep 命令的结果、代码结构、技术实现等细节，但你凭借常识判断出"人会主动发现问题"这个假设是错误的。这正是人类在 AI 时代不可替代的价值。

## 第四章：AI Agent 软件工程的根本性假设修正

### 4.1 传统假设的错误

我最初的分析错误地假设：

| 设计假设 | 人 | AI Agent |
|----------|---|----------|
| 会主动检查 | ✅ | ❌ |
| 会记住教训 | ✅ | ❌ |
| 会理解上下文 | ✅ | ❌ |
| 会质疑不完整 | ✅ | ❌ |

### 4.2 修正后的假设

经过讨论，我们共同认识到这个表格本身就是错误的。正确的理解是：

| 角色 | 行为模式 | 流程设计含义 |
|------|----------|--------------|
| 人 | 会偷懒、应付、走形式 | 需要威慑机制、审计追踪 |
| AI Agent | 精确执行、只做明确要求的 | 需要**强制**约束、**自动**验证 |

**关键洞察**：

不是"AI Agent 不如人会主动检查"，而是"机制必须从'期望人主动'转变为'强制系统执行'"。

### 4.3 新原则

基于修正后的理解，我们提出了四项核心原则：

| 原则 | 说明 | 传统方式的区别 |
|------|------|----------------|
| **强制约束 > 建议约束** | 不是"应该做"，而是"必须做" | 依赖人类自觉 |
| **系统自动验证 > 人工检查** | 系统自动发现缺口 | 依赖人类注意力 |
| **追溯关联 > 独立文档** | 需求-设计-代码-测试之间强制关联 | 文档独立存在 |
| **持久化记忆 > 依赖记忆** | 强制记录，自动加载 | 依赖人类记忆 |

## 第五章：动态 Checklist 机制设计

### 5.1 静态 checklist 的问题

传统评审 checklist 是静态的：同一份 checklist 适用于每个项目、每个文档、每个需求。这造成两个问题：

1. **噪音**：许多 checklist 项目与被评审的具体文档无关
2. **缺口**：文档特有的关键项目可能缺失

### 5.2 动态 Checklist 生成

我们提出了一个动态 checklist 机制，根据文档的实际内容生成评审项目：

```
┌─────────────────────────────────────────────────────────────┐
│  评审者（Agent 1 或 Agent 2）                                │
│                                                             │
│  1. 执行评审命令                                             │
│     oc-collab review requirements --file requirements_v2.md │
│                                                             │
│  2. oc-collab 分析文档内容                                   │
│     - 提取所有需求                                           │
│     - 识别依赖关系                                           │
│     - 生成动态 checklist                                     │
│                                                             │
│  3. 显示 checklist 和文档                                    │
│     Agent 逐项检查并记录结果                                 │
│                                                             │
│  4. 系统验证所有 checklist 是否完成                          │
│     - 未完成的检查项不允许签署                               │
└─────────────────────────────────────────────────────────────┘
```

## 第六章：人机协作模式

### 6.1 我们展示的模式

这次调查展示了一种新的人机协作模式：

1. **人类发起**：人类注意到 AI Agent 行为中的问题
2. **系统性调查**：人类和 AI Agent 一起追溯整个流程中的问题
3. **根因分析**：AI Agent 应用结构化思维（5-Why）寻找根本问题
4. **人类质疑与修正**：人类专家质疑 AI 的假设，引导走向正确方向
5. **共同设计**：人类和 AI Agent 共同设计改进机制
6. **文档化**：AI Agent 将整个过程捕获为可传递的知识

### 6.2 互补的优势

| 人类优势 | AI Agent 优势 |
|----------|---------------|
| 基于经验的上下文理解 | 结构化分析思维 |
| 对微妙问题的识别 | 系统性调查 |
| 创造性问题解决 | 完整文档化 |
| 对什么"重要"的判断 | 明确指令的执行 |
| **质疑隐含假设的能力** | **执行明确约束的能力** |

### 6.3 人类的核心价值

这次探索最重要的发现是**人类在 AI 时代不可替代的价值**：

- **不是与 AI 竞争技术能力**，而是提供 AI 所缺乏的判断力和质疑精神
- **不是关注技术细节**，而是直击问题的核心
- **不是执行具体任务**，而是确保任务方向的正确性

在这次案例中，你（人类专家）没有查看 grep 命令的结果，没有阅读代码实现，但你凭借常识判断出"人会主动发现问题"这个假设是错误的。这直接引导我们找到了真正的根因：不是"AI 不如人会主动"，而是"机制必须从期望主动转变为强制执行"。

## 第七章：结论与启示

### 7.1 关键发现

1. **AI Agent 需要与传统人类开发者完全不同的流程控制**，这不是因为 AI Agent 更差，而是因为它们基于需要明确、可验证约束的不同范式运作。

2. **传统软件工程假设不能自动转移到 AI Agent 开发中**。"如果有什么缺失，有人会注意到"这个假设在"有人"是只做明确指令之事的 AI Agent 时是不安全的。

3. **人机协作的核心价值不在于人类执行技术任务，而在于人类能够质疑隐含假设、直击问题核心、引导 AI 走向正确方向**。

4. **动态、内容感知的机制（如动态 checklist）对 AI Agent 工作流程至关重要**，因为静态 checklist 无法适应被评审的具体功能。

### 7.2 对行业的启示

这次调查的影响超越 oc-collab：

- **对于 AI 开发框架**：必须包含强制约束机制，而不仅仅是建议
- **对于 AI 项目管理**：必须实施系统性验证，而不仅仅是文档存在性检查
- **对于 AI 质量保证**：必须针对 AI Agent 行为模式设计，而非人类模式
- **对于 AI 政策和治理**：必须认识到 AI Agent 的独特特征并设计适当的控制

### 7.3 前行之路

缺失的 session_start 功能不仅仅是一个 bug——它是 AI Agent 时代软件工程根本挑战的一扇窗口。通过系统性地调查这个缺口，我们已经开始绘制适合 AI Agent 的软件工程实践领域。

这份论文记录的不仅仅是一个解决方案，更是一种**思考问题的方式**——如何通过人机协作，发现并修正隐含的假设，从而找到真正有效的解决方案。

探索的旅程仍在继续。随着 AI Agent 变得越来越有能力、越来越普遍，对适当工程实践的需求只会增长。这份论文是对那场持续对话的贡献——记录一个小的缺口如何带来大的洞察，以及人机协作如何系统性地发现和限制我们集体潜力的隐藏假设。

## 附录：方法论

### A.1 5-Why 技术

5-Why 技术是一种根因分析方法，通过反复问"为什么？"（通常五次）从直接症状深入到根本原因。

在我们的调查中：

1. 为什么功能缺失？→ 没有设计，没有测试，没有代码
2. 为什么没有设计/测试？→ 需求不清晰，没有被当作独立功能
3. 为什么评审没发现？→ 流程只检查文档存在
4. 为什么流程这样设计？→ 假设人类会验证功能
5. 为什么假设对 AI 失败？→ **这是错误的问题**

**关键转折**：在第五步时，人类专家质疑了前四步的隐含假设，指出"人会主动发现问题"本身就是错误的。这引导我们找到了真正的根因：机制必须从"期望主动"转变为"强制执行"。

### A.2 动态 Checklist 算法

```python
def generate_review_checklist(document_path: str, document_type: str) -> Checklist:
    """
    根据文档内容生成评审 checklist
    """
    checklist = []
    
    # 基础检查（所有文档通用）
    checklist.extend([
        CheckItem("格式正确", "文档格式符合模板要求"),
        CheckItem("版本信息", "文档包含版本号和更新日期"),
        CheckItem("完整性", "所有章节内容完整"),
    ])
    
    # 需求专项检查
    if document_type == "requirements":
        requirements = extract_requirements(document_path)
        for req in requirements:
            checklist.extend([
                CheckItem(f"需求 {req.id} - 唯一ID", "需求是否有唯一标识"),
                CheckItem(f"需求 {req.id} - 验收标准", "需求是否有明确的验收标准"),
                CheckItem(f"需求 {req.id} - 描述完整", "需求描述是否完整"),
                CheckItem(f"需求 {req.id} - 设计关联", "是否有对应的设计文档"),
                CheckItem(f"需求 {req.id} - 测试关联", "是否有对应的测试用例"),
            ])
    
    # 追溯性检查
    orphan_items = find_orphan_items(document_path)
    if orphan_items:
        checklist.append(CheckItem(
            "追溯性",
            f"发现 {len(orphan_items)} 个未关联的条目，需要处理"
        ))
    
    return checklist
```

## 附录：oc-collab 项目背景

### B.1 oc-collab 是什么

oc-collab（OpenCode Collaboration）是一个**双 Agent 协作开发框架**，基于 OpenCode 平台实现。它的核心目标是解决 AI Agent 独立开发时的混乱问题，通过引入产品经理（Agent 1）和开发（Agent 2）的分离式协作，确保开发过程规范化、可追溯、可复用。

**项目定位**：为 AI Agent 提供类似传统软件工程的流程约束，但不依赖人类监督。

**核心价值**：
- 双代理协作：产品 + 开发，互相监督
- 里程碑签署：质量门禁，不跳过
- 状态管理：单一事实来源
- 问题追踪：不重复踩坑
- 记忆机制：记得教训

### B.2 v2.2.0 功能清单

oc-collab v2.2.0 于 2026-02-02 发布，包含以下核心功能：

| 模块 | 功能 | 说明 |
|------|------|------|

| 项目管理 | project_manager.py | 任务分配、依赖管理 |

**测试覆盖**：164 测试，88% 覆盖率。

### B.3 协作流程详解

oc-collab 的协作流程基于传统软件工程的阶段划分：

```
需求评审 → 设计评审 → 开发完成 → 测试通过 → 部署上线
    ↓          ↓           ↓          ↓         ↓
   签署       签署         签署       签署      完成

每个阶段必须双方签署后才能进入下一阶段
```

### B.6 签署机制详解

oc-collab 的签署机制是质量门禁的核心：

**签署条件**：
1. 双方必须都完成签署
2. 签署前必须通过自动检查
3. 签署后状态更新为 "APPROVED"

**签署流程**：
```
1. Agent 1 (产品) 完成评审，更新 pm_signoff: true
2. Agent 2 (开发) 完成评审，更新 dev_signoff: true
3. 系统检查所有前置条件
4. 双方签署完成，phase 推进到下一阶段
```

### B.7 记忆机制详解

oc-collab 的记忆机制用于解决 Agent 会话隔离问题：

| 记忆类型 | 文件位置 | 内容 |
|----------|----------|------|
| 问题模式 | state/memory/patterns.yaml | 已知问题及其解决方案 |
| 决策历史 | state/memory/decisions.yaml | 重要决策及其理由 |
| 经验教训 | state/memory/lessons.yaml | 项目经验总结 |
| 待处理事项 | state/memory/pending.yaml | 当前待办 |

**Compaction 保护**：Compaction 操作前会导出所有记忆文件，确保不丢失关键信息。
